Process Mining

The focus of process mining is to discover, monitor and improve real processes by extracting knowledge from event logs readily available in today's information systems

Process mining techniques includes:

  1. Automated process discovery (extracting process models from an event log)
  1. Conformance checking (monitoring deviations by comparing model and log)
  1. Model enhancement (model extension and repairing)

Process models are expressed via process notation: Petri Net or BPMN

Petri net, a mathematical modeling language for describing distributed systems.

  • It is a bipartite graph in which nodes represents transitions and places, connected by arcs
  • A transition is an event that may occur, and is represented by a bar
  • A place is a condition and is represented by a circle
  • arcs run from a place to a transition (input place) or vice versa (output place)
    • never between places or between transitions

Places may contain a discrete number of marks called tokens.

  • A distribution of tokens over the places represents a configuration (marking) of the net
  • A transition is fired if it is enabled, i.e., there are sufficient tokens in all of its input places.
    • When the transition fires it consumes the required input tokens and created tokens in its output places.
    • A firing is atomic (single non interruptible step).
    • Unless otherwise specified, when multiple transitions are enabled at the same time, any one of them may fire (non determinism).

In pure petri nets the behavior can be specified with arc multiplicities: a
transition t is enabled at marking m if every input place p of t contains at least as
many tokens as the multiplicity of the arc from p to t is.

Process algebra is a family of formal approaches used in computer science to model concurrent systems

  • algebraic laws to manipulate, analyze and permit formal reasoning about processes
  • PetriNets can be translated in BPMN

As event logs contain only sample behavior, they should not be assumed to be complete.

  • Open world assumption: the fact that something did not happened doesn’t mean that it cannot happen
  • useless to have too complex models to explain the data
  • this model is too general for the event log

Mining is an optimization task of the model

There are four competing model quality dimensions: challenging to balance all of them

  1. fitness: to allow for most of the behavior seen in the event log
  1. simplicity: to allow for the most compact representation of the log
  1. precision: it does not allow for too much extra behavior w.r.t the log
    • If not precise is underfitting
  1. generalization: it does not restrict behavior to just the log
    • if not generalizable is overfitting

Three important categories of mining algorithms:

  1. Deterministic mining algorithm: it always delivers the same result for the same input. e.g. the alpha-algorithm (2002)
  1. Heuristic mining algorithm: it also uses deterministic algorithms but they incorporate frequencies of events and traces for reconstructing a process model, disregarding infrequent paths in order to manage complexity.

  1. Genetic mining algorithm: it uses an evolutionary approach to find a satisfactory solution by iteratively selecting individuals and reproducing them by crossover and mutation over different generations.

Logs

Event logs contain a set of events.

  • A single event has a unique event ID, it refers to one individual case, it has a timestamp, and it shows which resources executed which task.
  • It is a minimum requirement that the events refer to (i) one case [e.g. patient ID], (ii) one task, and (iii) a point in time

Alpha algorithm

Assumptions:

  1. logs are chronologically ordered
  1. each event refers to a single case (one caseID associated)
  1. each event refers to a specific activity of the process
  1. each activity of the process is included in the log
  1. the log is behaviorally complete in the sense that if an activity a can be directly followed by an activity b, then there is at least one case in the log where we observe ab
  • Workflow log maps letters to activities (a = check stock availability, …) and discards repetitions
Case 1: A → B → C → D
Case 2: A → B → C → D
Case 3: A → B → C → D
Case 4: A → C → B → D
Case 5: A → C → B → D
Trace 1: A → B → C → D  
Trace 2: A → C → B → D

  1. The algorithm looks at pairs of activities in the log and classifies their relationship

The Alpha Algorithm cannot tell the difference between:

  • True parallelism (activities happening at the same time)

  • Short loops (activities repeating in a sequence)
    • a → b → d
    • b → c → b loop

Both models can produce workflow that yield b||c because both bc and cb are observed

  • the parallel can be created only if no bcb sequences are obseved on the logs
  • To determine potential parallelism in 10 concurrent tasks, the number of
    required different cases to observe is 10! = 3,268,800
  • Preprocessing can be also used to collapse repetitions (like aa and bb) to a single execution

Conformance Checking

Conformance checking is concerned with the question whether or not the execution of a process (event logs) follows constraints (model)

  • replay each trace in the event log in the model

The idea is to compare at each step the number of tokens that are required for replaying an activity with the actually available tokens.

At each step, we might observe situations of conformance and non conformance. In case of conformance, we count the following four facts:

  • p: # of output tokens correctly produced by a model element [previous element]
  • c: # of input tokens correctly consumed by a model element [next element]
  • m: # of missing (unproduced) output tokens, e.g. because something did not occur

  • r: # of input tokens remaining unconsumed, e.g. because something did not occur although the model expected it to happen

  1. Finds the best model using costs:
    • Uses A* algorithm (like finding shortest path on a map) [modification of dkjstra]
    • Assigns costs to:
      • Skipped activities (activities in model but not in log)
      • Inserted activities (activities in log but not in model)
    • Finds the model with minimum total cost = best fit
  1. Uses projection: groups related events together and project the log on those to simplify the mining

INDUCTIVE MINER Discovers block-structured process models (clean, hierarchical processes without spaghetti)

  1. Divides and conquers:
    • Splits activities into groups
    • Finds the most important process structure (sequence, choice, parallel, loop)
    • Recursively splits further until it reaches single activities (base case)
  1. Creates a process tree:
    • Leaves = activities (a, b, c, etc.)
    • Nodes = operators that combine activities:
      • × (XOR) = exclusive choice (either A or B)
      • → (Sequence) = sequential (A then B)
      • ∧ (AND) = parallel (A and B simultaneously)
      • ⟳ (Loop) = repetition (repeat A)

Simplicity is measured by comparing the number of elements ( #gateways + #sequence flows + #activities) of the model M with the number of activities (cardinality of) in the log
