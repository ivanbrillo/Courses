Erlang Intro

Two programming paradigms:

  1. Imperative: sequence of commands that change the program state
  1. Functional: computations as evaluation of expression/function → lack of state during computation
    1. No side effects
    1. Referential integrity / pure functions
    1. Lack of state
    1. Eager / lazy evaluation
    1. First-class functions & Higher-order functions
    1. Primary role of recursion
    1. Use of recursive data structures - lists

An expression is said to be referentially transparent if it can be replaced by its value with no change

  • such expression has no side effect

A function is called pure if its call are referentially transparent

  • whenever it hold, we can formally reason on the program as a rewriting system
    • sequences of discrete steps where one term is replaced with another

Lack of state → No mutable variables (no classical assignments)

  • A variable is immutable, once bounded to a value it cannot change

Eager Evaluation → evaluated an expression as soon as it’s encountered

  • usually adopted in call by value or reference in function

Lazy Evaluation → postponed to the time it’s value will be really needed

  • often they return a function that represent the computation to get to the result

Recursion

Without the help of state variables, recursion is the only way to support repetion of specific computation

  • has the same expressing power of interative methods

Tail Call Optimization: whenever the last executed operation within a function call is another function call, we can substitute the caller’s frame, no need to keep them both

Recursive data structure: linked list as first element + list

Concurrency

data-races → data mutability

Mutable states requires synchronizaion

  • In imperative languages concurrent computations must be explicit specified (eror prone es: locking with deadlock)
  • Pure functional programming is thread-safe, where sub-expression can be evaluated in parallel

Erlang

Is executed by ERTS (Erlang run-time system) via intermediate language (compilation is needed)

  • The bytecode is run over a dedicated virtual machine (BEAM) → it uses it’s own schedulers (one per CPU) to distribute the work

BEAM use a separate process queue per scheduler + work stealing to load balancing

It has a garbage collector

Functions exported by modelus can be accessed after module loading

The simplest expression is called term and can be expressed as literal

  • a variable is an expression
  • Size:
    • Tuples: Fixed size, known at creation time
    • Lists: Variable size, can grow/shrink
  • Access:
    • Tuples: Direct access to any element (O(1))
    • Lists: Sequential access, must traverse for nth element (O(n))
  • Memory:
    • Tuples: Contiguous memory, elements stored together
    • Lists: Linked structure, elements can be scattered
  • Use Cases:
    • Tuples: Structured data with known number of elements (like records)
    • Lists: Collections that need to be processed sequentially or modified

  • augment the power of pattern matching for function
  • No user defined function can be used in guards (sure there is not side-effects)
