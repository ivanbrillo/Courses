Erlang Distributed Application

Possibility to spawn processes on remote nodes and machines

  1. Distributed Erlang: programs run on nodes, with their own set of processes. Any processes can interact across nodes
  1. Socket-based distribution: more secured, based on sockets

Each machines can hold more than one nodes → Erland node (spawned when type erl)

  • Each node is connected to the others

Nodes must be given unique names to be contacted. The format is: Name@Host

eg. ale@localhost

Cluster: connection of nodes

  • I can use just one of name types
    • Long names with fully qualified domain names
    • Short Names w/o “.”

EPDM (Erlang Port Mapper Deamon) runs on port 4369 in each machines in the cluster, acting as a name server, enabling contacts across nodes.

Two nodes are connected the first type they try to comminicate

net_kernel:connect_node(tom@localhost).  # or ...
net_adm:ping(Node)
  • Transitive connection: If node X is connect to Y, then Y will be connected with all the nodes connected to X

Nodes from different clusters are not allowed to connect.

  • the trick is to use a cookie shared by all nodes of a cluster

Spawn processes remotly

spawn(tom@localhost, fun() -> io:format("w", [node()]) end).
  • The output is kept and displayed on me and not in the remote machine
  • Remote PID node()→ the first number in not zero

Modules provided to support distributed Erlang programs:

  • net_kernel - to connect/disconnect nodes, to switch a node to distributed/non-distributed, to control heartbeat...
  • global - a global process registry → use global:send(Name, Msg); handles name conflicts
  • rpc - functions to execute commands on remote nodes → rpc:call(Node,Mod,Funct,Args) returns locally whatever is returned by the function executed remotely; rpc:call/5 specify a timeout for asynchronous computing

OTP - Open Telecom Platform

Tool for boosting development of Erlang programs

  • OTP Behavior: a behavior encapsulates common behavioral patterns. It's described as an application framework that can be parameterized by a callback module. This means that behaviors provide a generic structure for certain types of tasks, which can be customized for specific use cases (es. gen_server)
  • Callback function is a function that is pass by a caller in order to be called later. Can be synchronous callback if it is exectued before the called function return or deferred callback when it is executed after (used by event handling es gui)

Separation of Concerns in OTP:

  • Non-functional issues are handled by the Behavior
  • Specific Functional issues are handled by the Callback (custom) module

OTP gen_server (behavior)

  • Call synchronous request, while cast unsynchronous
  • The callback module must specify -behaviour(gen_server).This Erlang attribute tells the compiler that this module is intended to be a callback module for gen_server.
  • call is syncrounous, meanwhile cast in unsyncronous

Dealing with errors

Erlang is intended to support the development of fault-tolerant systems, thus runtime errors must be handled

  • Error Handling in CONCURRENT programs - we need to deal with errors at the process level, in collection of processes. In case of a process crash, we want another process may detect the event, and take over the job of the crashed process.
try
    % Block of code that might cause an error
    Expression
[of]
    % Handle the successful result
    Pattern -> SuccessCode
catch
    % Handle exceptions (errors, throws, exits)
    Class:Exception -> ErrorHandlingCode
[after]
		% Like finally in other langs
		Expression
end.

Links

A special relationship between processes can be set up, to let us terminate a set of related processes in case one of them would fail. BIF: link/1, and spawn_link/1-3

  • The other process dies if it is not a system process

System Process

I can catch process signals by making the recipient a system process.

Any exit signal to a system process is converted to a regular message. Upon receiving it, we can decide what to do, maybe, restarting the dead process!

  • Special case: kill reason → never trapped; an ultimate weapon! The recipient of “kill” will send out the “killed” reason
process_flag(trap_exit, true),
receive
    {'EXIT', Pid, Reason} ->
        io:format("Process ~p exited with reason ~p~n", [Pid, Reason])
end.

Monitor

A more flexible kind of relationship can be set up via monitor/2-3, and spawn_monitor/1-3.

Differently from links, monitors

  • are unidirectional;
  • can be stacked (1+ instances per ordered pair).
  • Does not coupled its life (unless system process) to the other process

As a monitored process goes down, the monitoring process receives a message whose pattern is
{'DOWN', MonitorRef, process, Pid, Reason}.
