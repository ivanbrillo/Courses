Remote Call

Direct vs Indirect Communication

  • Direct communication - each of the involved parties directly refers to the counterpart
  • Indirect communication - fully asynchronous relationship, by leveraging an intermediate system that delivered the message

Direct Communication

Request/Replay Protocols

Request/reply protocols support low-level client-server interactions.

  • Typically synchronous: the client sends a REQ, and stops waiting for a REPLY (the reply plays also the ACK role)
  • Usually, UDP-like models (guarantees that are offered by the UDP protocol) + no restriction on datagram length

General Primitives

public byte[] doOp(RemoteRef s, int opId, byte[] args); // target server (ip:port) 
public byte[] getRequest();
public void sendReply (RemoteRef c, byte[] reply);
  1. doOp() sends a request message to the remote server identified by s, to request the specific operation opId with arguments marshalled in args, and returns the reply.
  1. Blocking operation, gets the request message (server side)

Structure of a Message

Any message is uniquely identified by a requestId

  • assigned at the middleware level
  • plus the address of the sender (IPaddr+port) is a unique code to identify the message

Marshalling

The exchanged data in the context of a REQ-REPLY communication could be highly structured (ob)

  • The two parties must agree on how to encode the exchanged data, so to correctly reconstruct all data items.
  • The transformation of the memory representation of an object to a data format suitable for transmission is said marshalling (and un-marshalling the opposite operation).
  • Not important if I use a single language, because all the types are equal

Failure Model

Regarding the transmission medium, along with UDP

  • possible message loss
  • possible message reordering (depends on the routing)

Regarding processes: usually, fail-stop → unresponsive process is interpreted as not alive

  • To check whether the server is down, a timeout is employed in the implementation of doOp

  1. Timeout, to check possible server failures
  1. Request retransmission, to compensate for possible loss of req messages (ask n times the same req)
    1. Duplicate filtering: 1+ copies of the same message may arrive, so duplicates must be discarded → through requestID

Re-execution vs caching on the server side

  • caching is possible only for idempotent requests (If pure function then by definition are idempotent)
  • Client could help for cache flushing (saying that the op will not be executed anymore)

if f is called subsequently twice with the same arguments, the second call will have no side effects and will return the same output as the first call.

HTTP

  • Methods: types of messages, intended for semantically different classes of operations. GET, POST, etc.
  • Idempotence: the side-effects of N > 0 identical requests are the same as for a single request → caching of results is possible!
  • Nullipotence (or “safety”): msgs determine retrieval, no state change on the server

HTTP pipelining: sending requests one after the other without waiting for each reply before issuing the next request.

  • Of course, this cannot be done in case of non-idempotent requests.
A client that pipelines requests SHOULD retry unanswered requests if the connection closes before it receives all of the corresponding responses.
  • No specific Marshalling is used in HTTP but specify how the object should be interpreted (MIME specification)
    • MIME is a two-part identifier for file formats and format contents transmitted
      on the Internet: type/subtype (text/plain text/html)

RPC - Remote Procedure Call

It’s a form of inter-process communication (not nodes!) between a client and a server. The requested operation is the execution of a procedure on the server, getting back results

  • In general server/client could be implemented in two different languages
    • Interface-based programming → abstraction and portability
  • Diverse call semantics on how it is chosen or implemented by the middleware
  • Transparency wrt access, location → I don’t want to specify all the parameters

Interfaces for RPC

RPC interfaces are specified using an IDL (Interface Definition Language)

Interface specifications → cross-language interoperability, because they are used to map parameters onto each specific way to use them. (eg. long type)

  • An interface definition is usually compiled by using specific tools, so to obtain the modules (stub/skeleton) to be deployed on the different nodes to support the communication.

Parameter Passing

The ordinary “local” way to deal with parameter passing cannot be plainly extended to the distributed setting: peers don’t share an address space

  • so the usual pass-by-reference convention does not make sense: ordinary addresses cannot be passed as params!

Instead, as in pl/SQL (procedural SQL), usually a parameter can be specified as

  • IN (input only)
  • OUT (output only)
  • INOUT (input in Request, output in Response)

Faults

Local calls have the exactly-once semantics → ask once a result and receive one response

  • not possible in a distributed setting → may be needed to be asked multiple times
  • trick applied in the middleware, not by the programmer

Implementation

STUB

  • It provides the same interface as the remote service, allowing the client to call methods as if they were local → marshalling

SKELETON

  • A skeleton is the server-side counterpart to the stub.
  • It receives the request from the stub, unmarshals the parameters, and invokes the appropriate method on the actual server object.
  • After execution, it marshals the result and sends it back to the stub.
  • There are multiple SKELETON for each service that could be called

gRPC (Google RPC)

It’s an open-source, high-performance implementation of a Remote Procedure Call system.

  • efficient connection across distributed software modules (services)
  • default IDL for service/APIs is Protocol Buffers - a.k.a. Protobuf (Google’s language-neutral extensible mechanism for serializing structured data)
  • “pluggable” support for load balancing, tracing, health checking and authentication

Idea: define a service interface w/ methods, using ProtoBuf.

  • ProtoBuf is used also for defining data structures/messages in a language-independent way, as well as its serialization.
  • On the server side, the server implements this interface and runs a gRPC server to handle client calls.
  • On the client side, a stub with the same interface provides access to the remote service methods, hiding the communication details

Steps:

  1. define the desired structuring for your data (called “message”) in a .proto file
  1. use special automatically generated source code to easily write and read such data to and from a variety of data streams (files or communication channels)

The same approach fits the communication needs in client/server systems.

  • automatically get the class of the message (by a software)
  • message objects are immutable, and they can be created via the relative builder; a builder has “setter” methods for the message fields, which can be concatenated
  • resemble a local call, but it is a remote call, so I need to handle some exception

A stub on the client can communicate with the gRPC server through a “channel”, which represents the connection to the server at a specific IP address and port.

  • In practice: a channel must be created first, and the creation of a stub by a factory method requires the specification of the relative channel.
  • gRPC supports both blocking/synchronous and streaming communication → different stubs are required for the two.

RMI - Remote Method Invocation

  • As RPC: programming by interfaces (no need of IDL), implements call semantics and adresses transparency issues.
  • Use JVM so no need to handle heterogeneity in programming languages

Additional features, not available in RPC:

  • Object orientation - support to remote objects
  • Use of remote references - as parameters as well
  • Use of exceptions - also for anomalous conditions related to communication (java.rmi.RemoteException)

New issues:

  1. Class loading - how to implement it in a distributed setting? (because the class definition may be remote)
  1. Garbage collection - how to account for remote references hold by remote client objects?

Remote References

RMI extends the concept of (local) reference to a (local) object: a remote reference is the means to access a remote object.

  • It is an ID for a particular unique remote object in the whole system;
  • it is created by RRM (Remote Reference Module), a dedicated component.
  • creation time and object number to identify the unique object
  • then I can add some infos about the interface of the object → understand what methods I can call

Remote Interfaces

An object is a remote object if it implements a remote interface, which is an interface that declares a set of methods that may be invoked from a remote JVM (“client”).

  • An interface is “remote” if it at least extends (possibly indirectly) java.rmi.Remote, which is a marker interface (no method) → let the system know what type of code it will handle.
  • Each method declaration in a remote interface (or its super-interfaces) must be a remote method declaration:
    • include java.rmi.RemoteException (or one of its super-interfaces) in its throws clause, in addition to any application-specific exceptions → let the system know of possible communication problems
    • In a remote method declaration, a remote object declared as a parameter or return value (even if embedded within a non-remote object in a parameter) must be declared as the remote interface, not the implementation class of that interface → as it would be with IDL

Parameter Passing

In RMI, for remote methods of remote objects, arguments are IN, the return value is the only OUT.

  • Ordinary “by value” → must undergo marshalling, thus are required to implement Serializable
  • Remote references → they must be typed as Remote (interface)
  • Green part automatically build up by the system. In Java <5 has to be used a particular compiler

Client:

  1. Proxy: local counterpart of the remote obj → in charge of marshalling/unmarshalling
    1. based on the relative remote interface
  1. RRM on both sides, creates remote references and a table (ROT) keeps the match between remote/local references

Server:

  1. The communication module ask the RRM for the local reference of the dispatcher/skeleton
  1. The dispatcher, based on opID, determines the method to invoke on the skeleton
  1. The skeleton perform the unmarshalling and invokes the correct method on the object

Find Remote Objects

A servant can be accessed once its remote reference is available. How to find it? We can exploit a registry, namely rmiregistry, to lookup remote refs from names (i.e. it acts as a name service).

  1. A servant binds to rmiregistry, making its remote references available on it
  1. Any client can lookup the relative remote reference in the rmiregistry
  1. Using the remote reference, the actual call can be executed

Remote Reference:
The object returned from the registry lookup is a stub (proxy). This proxy implements the remote interface and handles:

  • Marshalling the method parameters.
  • Sending the request over the network.
  • Receiving the response and unmarshalling it.

RMI Multithreading

Typical possible approaches:

  1. Thread-per-request - Each request is handled by a separate thread
  1. Thread-per-connection - One thread dedicated to a single connection
  1. Thread-per-object - Requests to a single servant objects are serialized over one dedicated thread

  • Calls originating from different clients Virtual Machines will execute in different threads.
  • From the same client machine it is not guaranteed that each method will run in a separate thread

The code related to request processing must be thread-safe

Class Loading

Dynamically performed when call new

It is normally performed by Class Loaders

They are organized in a delegation hierarchy

  • A classloader asks first its parent to load a class and, in case it fails, it tries to perform the task on its own.

  • Properties of class loading: uniqueness (loaded only once), visibility (means a class loaded by a specific loader can be accessed by other classes loaded by the same or child loaders).

Class loading can be performed remotely, by downloading .class files from specific server nodes. The location can be specified in two ways:

  1. The remote reference can be annotated with this information (URL) → when client connect for the first time to a remote object (otherwise how to deserialize)
  1. The object sent as a parameter in a remote method call is annotated with the URL → when client pass the object to the server

Classloaders are informed on where to load classes by the codebase property, i.e. for RMI: java.rmi.server.codebase

Garbage Collection

Each reachable object is marked first, and then all the unmarked objects are removed (swept away).

The marking algorithm starts from a pool of GC root objects. In Java, the GC roots are:

  1. local variables in the main method
  1. the main thread
  1. static variables of the main class

It requires to stop the execution of the program to perform the marking

  • it may take a lot of time

Tri-Color Marking

Does not require freezing the system. Main alg to perform GC

  • allow interleaving with the main program

Three sets of object

  1. White: candidates to be swept
  1. Grey: objects that are reachable from roots (not scanned yet for references to white)
  1. Black: not canidates for garbage collection (no references to objects in white)

At init, Black is empty, Grey contains the objs directly reachable by roots, White has all the rest

while !Gray.isEmpty():
	 Pick one obj X from Grey, and move it to Black; 
   Move into Grey all the objs in White that are referenced by X
remove all objects in White

Property: no obj in Black has a ref to objs in White

  • Thus, when Grey becomes empty → all the objs in White can be swept.

Reference Counting

Each object keeps a counter of (incoming) references. Object references added/removed → the counter is updated

  • The GC is allowed to remove all objects whose counter = 0
  • Problem: possible cyclic references lead to memory leaks! Thus, some periodic checks for this must be done → when a cycle is disconnected from root it will not have the counter to zero

In java local GC is usually implemented using Mark&Sweep approaches.

Different objects show different utilization patterns (typically, high “infant mortality” is observed), and this affects the GC performance.

  • For this reason, objects are divided into “populations” (e.g. young and old) according to their behavior, so to optimize the overall process (only younger objects are set to white).

Distributed Garbage Collection

Based on reference counting; Local GC & DGC must collaborate!

  • Clients should inform servers about what remote refereces they are using.
  • On the server, the Remote Reference Module must keep, for each ROT entry, the list of clients that hold remote references to that object (the “servant”).
  • Such a list has to be updated each time a remote reference is created/duplicated/removed.

The DGC functionality is described by the java.rmi.dgc.DGC interface, used for the server-side component of the overall system.

dirty(<list of rem refs>, ...  , <Client JVM_ID>)
clean(<list of rem refs>, ...  , <Client JVM_ID>)
  • Dirty invocation must be done by the RMI runtime just before constructing the proxies for the corresponding remote objects.
  • Clean is used to inform the server that the client makes NO MORE use of the reported remote references → removal of JVM_ID from the relative lists of “holders”.

Problems

  1. Consequences of a data race between clean(X, …) and dirty(X, …) when the list of holders for X has one single element

Solution: the server must be informed that X has been given to C, and a dummy placeholder for C is placed in the list of holders for X, waiting for the corresponding dirty(X) to come.

  1. Crashes of clients may prevent a list from ever become empty, leading to a memory leak.

    The semantics of dirty(…) has to be changed: dirty(...<Lease>) corresponds to ask for a lease time, and a Lease time will be returned.

    • It’s up to the client runtime to renew the lease by successively invoking dirty(…) . Whenever a Lease time expires without timely renewals, the client is removed from the list of holders.
