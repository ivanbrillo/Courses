Memory Consistency Model

The goal of a memory consistency model is to characterize, with a set of rules, the way operations towards memory locations are visible to processes.

  • The consistency model specifies a contract between the programmer and the system, so that the programmer can count on some guarantees about the behavior of memory operations.
  • The less stringent the consistency model is, the easier it will be to implement it in HW (and SW) components, in a more efficient way

Sequential Consitency

A write to a variable does not have to be seen instantaneously, but writes to variables by different processes have to be seen in the same order by all processors.

  • W1 e W2 are concurrent even if it comes before in the global time
  • They have to be seen in the same order for each process

Causal Consistency

Generalization of sequential consistency in a weaker model.

  • only causally-related writes must be seen in the same order by all processes
x = 1;        // Write A
x = x + 1;    // Write B (causally dependent on Write A)

PRAM Consistency

All processes see memory writes from one process in the order they have been executed by the process (as though they were “moved” to RAM through a pipeline).

  • No guarantee exists about the order in which different processes see writes from other different process (apart the “pipeline” rule).

Java Memory Model

JMM implicitly specifies the set of all admissible executions; a JVM (+ compiler) must support a subset of these, possibly all.

  • Real-world JVMs sometimes do not strictly observe all limitations, causing small behaviour changes

  1. Program order rule: each action in a thread happens-before every action in that thread that comes later in the program order.
  1. Monitor lock rule: an unlock on a monitor lock (eg syncronize) happens-before every subsequent lock on that same monitor lock
  1. Volatile variable rule: a write to a volatile field happens-before every subsequent read of that same field
  1. Thread start rule: A call to Thread.start() on a thread happens before every action in the started thread
  1. Thread termination rule: any action in a thread happens-before any other thread detects that thread has terminated either by successfully return from Thread.join() or by Thread.isAlive() returning false
  1. Interruption rule: a thread calling interrupt on another thread happens-before the interrupted thread detects the interrupt (InterruptedException or by isInterrupted())
  1. Finalizer Rule: the end of a constructor for an object happens-before the start of the finalizer for that object (method called by the GC to release all the resources of that object)
  1. Transitivity: if A happens-before B, and B happens-before C, then A happens-before C.
