Web Services

Why a client should ask the help of a server to perform a computation?

  • When the client doesn’t have something locally (performance, resources, capabilities)

HTTP offer a standardized way to communicate with a server

  • lightweight protocol nowadays

Use HTTP to provide clients with a description of a service result

Needs to be formalized:

  1. required interactions
  1. formats of the results

Interoperability between software applications running on a variety of platforms and frameworks

  • From ordinary API to server Web APIs

Two different ways to develop web serveces

  1. Big web services → enphasis on service access on the application through specific application level protocol (like XML)
  1. RestFul WebServeces → enphasis on resource access. Classic HTTP methods are used, encoded via JSON or XML

Big Web Services

  • Use XML messagges according to SOAP (simple object access protocol) with XML encoding of data types
  • Formal description of the provided service by WSDL (WS description language) → similar to RPC
    • not used in reality
  • heavy weight developement, reduced by supporting IDEs
  • JavaAPI → jax-ws, making SOAP transaction transparent

  1. WSLD first (easly supported by IDEs) or Implementation First
  1. Broker Repository → UDDI standard (Universal description discovery and integration)
    1. publish the WSLD, so each client can access it
  1. Aimed at targeting SOA systems (service-oriented architecture)

RESTful Web Services

Lightweight

  • REST (representional state transfer) → not a standard but an architectural style
  • No XML messagges and no formal interface definition
    • producer and consumer must have a mutual understandin of the context
  • A resource on the server and HTTP requests towards it can either return a description of its state or update it
  • REST Constraint
    • Client server architecture
    • stateless-ness (no context)
    • Cacheability - clients and intermedietes can cache responses
    • Code on demand - possibility to transfer code
    • Rest uniform interface → fixed set of operations (HTTP)
      • PUT: create a new resources and DELETE deletes one
      • GET retrives the current state of a resource in some representation (HTML, JSON, XML)
      • POST transfer a new state to a resource

RESTful service should be call web API

  • The design of a proper API is crucial
  • Different proposed DLs (Description Language)
    • ex. OpenAPI → paired with graphical designers

SOA - Service Oriented Architecture

Service-Oriented Architecture (SOA) is an architectural pattern in software design where different services are provided to various components through a communication protocol over a network. In SOA, software components are modular and loosely coupled, making it easier to integrate and scale applications.

Existing application and on top of them I have some other services → composite services, that are organized to business process services

  • The interface defines how a service provider will perform requests from a service consumer
  • The contract defines how the service provider and the service consumer should interact
  • The implementation is the actual service code itself

JEE

Jakarta EE is a set of standardized APIs and specifications (like Servlets, JSP, EJB, JPA, etc.) for developing enterprise applications.

Typical organization of a (web) application: 3-tier architecture → a client-server architecture where:

  1. user interface,
  1. functional process logic,
  1. data access/data storage

Are developed and maintained as independent modules, possibly on separate platforms.

Container

At the middleware level, components can be organized in containers, and components managed within containers

  • A container, as well as any component, has both provided and requested interfaces

It’s up to the server to provide the resource, either retrieving it as a file (static content), or generating it on the fly by means of a program (dynamic content)

Common Gateway Interface (CGI)

A standard protocol for web servers to execute shell programs that dynamically generate web pages.

  • CGI scripts are usually placed in the special directory cgi-bin. Parameters are passed via environment vars and by std input.
http://xyz.com/cgi-bin/myscript.pl/my/pathinfo?a=1&b=2   // perl script
  • generally the server spawn a new process to execute the script

To improve performance, the code for content generation could be executed internally to the web server process → possibly using multithreading.

  • In Microsoft environments: classic ASP. In Jakarta EE: Servlets, and related technologies

Tomcat Web Server

Basic internal components:

  1. Coyote: HTTP “Connector,” listens on ports and forwards requests to the engine
  1. Catalina: “Engine,” Servlet container; it refers also to a Realm (DB of usernames, passwords, and relative roles). → run the web applications provided by the web server
  1. Jasper: JSP container
    1. JavaServer Pages → It converts JSP pages (which are HTML pages with embedded Java code) into Java Servlets that resolve to pure dynamic HTML
  • Jasper integrates tightly with Catalina. When a JSP request is received:
    1. Catalina forwards the request to Jasper.
    1. Jasper processes the JSP, generating a servlet if necessary.
    1. The servlet is handed back to Catalina for execution.

  • Valve: element to be inserted in the REQ processing pipeline

Supporting Components

  • Logger: Handles logging throughout different levels
  • Session Manager: Manages user sessions
  • Class Loader: Loads Java classes as needed
  • Listeners: Monitor and react to events

Host → virtual host name (example.com)

  • also more then one for server

What is after the first “/” can be mapped to different web applications → each of them is assigned a so called Context (represents a specific web application)

  • each of them has some resources (servlet and JSP)
  • The web app used to process each HTTP request is selected by Catalina based on matching the longest possible prefix of the Request URI against the context path of each defined Context

In the filesystem, one directory (appBase - by default, “webapps”) is used to keep all the material for web applications

  • Each web application has a dedicated folder inside webapps

Rules to obtain the base file name, given the context path:

  • If the context path is “/” → “ROOT”
  • If the context path is not “/” → base name = context path with the leading '/' removed, and any remaining '/' replaced with '#'

webapps/
├── ROOT        → Handles requests for `http://example.com/`
├── app1        → Handles requests for `http://example.com/app1`
├── nested#app  → Handles requests for `http://example.com/nested/app

web.xml

  • The deployment descriptor for the web application.
  • Used to define servlets, filters, and other components.

WEB-INF contains config files and custom Java classes and libraries needed for that application

  • cannot be directly addressed from outside (the browser)

To avoid interference of classes belonging to different contexts, different classloader hierarchies are used for each context.

Any loaded class is identified by its name AND the classloader that loaded it, so the same class used in two web apps might be loaded twice.

Servlets

Java classes/objects that respond to a request, aimed at producing the content for the response.

  • A class that implements the interface jakarta.servlet.Servlet
  • The thread-per-request model is generally applied → synch issues!

Servlets are kept in a container, which manages them.

  • Methods of servlet are meant to be invoked by the container → no need to create a main function
    • this is the most important step of the request processing pipeline (for builing the dynamic page)
  • The container is responsible for managing the lifecycle of servlets, and for mapping URLs to the corresponding servlets
    • usally with url pattern instead of single urls

Life-Cycle


Upon a REQ, service() is invoked → possibly, de-multiplexing to doPost(), doGet(), etc.

  • One-thread per request, so I don’t need to have different instances of this class

For a simple handling of HTTP requests/responses, request and responses are represented by corresponding objects, so that containers can easily take care of them throughout their processing pipeline.
According to Servlets specification, such objects must implement:

  1. jakarta.servlet.http.HttpServletRequest
  1. jakarta.servlet.http.HttpServletResponse
  • request/response objects are passed by the container to the servlet service method!

Req Parameters

Regardless of GET/POST mode, parameters can be accessed within the request object using the methods (ServletRequest interface):

  • getParameterNames() provides the names of the parameters
  • getParameter(name) returns the value of a named parameter
  • getParameterValues() returns an array of all values of a parameter if it has more than one values. Information in HTTP headers is retrieved in the same way.

Response

Two ways of inserting data in the body of the response message:

  • getWriter() returns a PrintWriter for sending text data
  • getOutputStream() returns a ServletOutputStream to send binary data

Both need to be closed after use!

  • Setting headers’ content: specific methods, e.g. setContentType(<MIME_type>)

Mapping URL to Servlets

Specified in the webapp deployment descriptor web.xml in two steps:

  1. from URL pattern to servlet name
  1. from servlet name to servlet class

Alternative way: directly in the code, using annotations:

@WebServlet(
	name = "MyAnnotatedServlet",
	urlPatterns = {"/foo", "/bar", "/pippo*"}
)
public class MyServlet extends HttpServlet {
	// servlet code
}
  • type of annotations that are present in the .class file so external tools can extract this metadata (tomcat check in the classes that extends servlets)

Default Servelet

In Tomcat, ordinary handling of static contents (e.g., html pages, images, etc.) is performed using a dedicated “system” servlet:

  • DefaultServlet, which is called for any REQ URL referring to static content.

Implementation class: org.apache.catalina.servlets.DefaultServlet, which extends the abstract class HttpServlet

  • Specific ways to access content depends on its settings, e.g., it is possible to specify if directory listing is allowed or not (html page with all files of the directory)

Grouping requests into Sessions

A series of queries from the same client may be semantically related, i.e., may correspond to several interactions along time belonging to one specific conversation. Such groups are called sessions.

  • cookies expiration, login, shopping cart and so on…

Sessions can be defined by setting a maximum distance between adjacent requests; different values result in different “clusters.”

Session Tracking

Sessions can be specified by setting a timeout value, to be reset as a new request in the same session arrives.

  • The web server must be able to identify sessions (assigning “SessionIDs”), and to determine whether a request belong to a certain session.
  • Sessions are represented through specific objects (interf. HttpSession) that have to be shared across all the servlets accessed by the same client.
  • Programmatically, session objects can be obtained from requests:
    HttpSession mySess = req.getSession(boolean create);
    • Crete a session if there is not any session related to the request
    • It’s just an interface, we don’t know what is the underlying class → web server specific, but the same code is portable

  1. Making use of cookies (standard) → they have an expiration date
    1. For tomcat the name they are called JSessionID
  1. Hidden fields → in HTML I can add an element that is not rendered, with some infos associeted to it, so the server that provide the HTML content to the client will add also an hidden field with the session identifier
  1. URL rewriting → embedd the session ID inside the URL 
    http://www.example.com/page?sessionID=abc123

Session Objects

A specific HttpSession object has to be used for every ongoing session.

  • The webserver marks each new session with a unique “SessionID”; session objects can be kept in an associative array, with SessionIDs as keys.
  • Any REQ message that belongs to a certain session, must be associated to the relative SessionID: this makes the container able to retrieve the correct session object from any servlet.
    • In tomcat each object has a manager in charge of session objects

State info in Session objects is kept as a set of attributes, each identified by a key, accessed via methods:

public void setAttribute(String name, Object obj)
public Object getAttribute(String name)

Optionally, sessions can be invalidated:

mySess.invalidate()   // immediately
mySess.setMaxInactiveInterval(int interval)  // max interval  between 
              //successive requests (default value defined in web.xml)

Servlet Filters

Upon receiving a REQ, often some typical actions have to be undertaken.

  • E.g. recording, IP logging, input validation, authentication check, encryption/decryption, etc.
  • I can specified a base URL that from there it must be checked

Each action can be carried out by a pluggable server-managed component named servlet filter

  • Before reaching the final destination the request will be passed through a series of filters
  • Whether applying or not a filter to a REQ depends on the match between the REQ URL and the pattern specified for the filter
  • Pros: separation of concerns (different pieces of SW/different tasks), easy maintenance
  • APIs: in jakarta.servlet, interfaces Filter, FilterChain, FilterConfig

A custom servlet filter must extend Filter → and implement the methods

init()
destroy()
doFilter(ServletRequest req, ServletResponse resp, FilterChain chain)

To pass the REQ to the next component → chain.doFilter(req, resp);

  • Mapping of filters: as for servlets, in web.xml or using annotations
@WebFilter(filterName = "TimeOfDayFilter", urlPatterns = {"/*"},
       initParams = {@WebInitParam(name = "mood", value = "awake")})
 public class TimeOfDayFilter implements Filter {}

Servlet Collaboration

It is possible to make servlets/resources collaborate for the construction of the response content via the RequestDispatcher interface.

  • A RequestDispatcher can be obtained from the ServletRequest object by the factory method request.getRequestDispatcher(<targetResource>)
  • The argument identifies the servlet/resource we want to collaborate with.

Two possible types of collaborations:

  1. Obtaining content to include
    rd = request.getRequestDispatcher(<targetResource>);
rd.include(request, response);
  1. Delegation of request handling
    rd = request.getRequestDispatcher(<targetResource>);
rd.forward(request, response);

Sharing Infos across Servlets

As servlets can possibly collaborate, they may need to share information.

Information sharing can be obtained with standard objects created by the container, and made available to servlets: scope objects

  • They are equipped with the methods setAttribute/getAttribute.
  • Among them:
    • Request relative to one http transaction (request scope) → in req obj, useful for jsp or filtering
    • The session object (session scope) → keeps infos across sessions
    • The ServletContext obj, one per web application (web scope)

Structuring

Servlets are a basic technology that imposes no constraint on how a whole application should be structured.

  • Risk: Magic Servlet antipattern, where issues about different aspects of the application are dealt within the same method.
    • For example, a servlet that is responsible for:
      • Handling HTTP requests
      • Processing business logic
      • Managing database connections
      • Rendering views (HTML)
  • Solution: define specific roles, so that a specific task/concern refers to a distinct software component.
    • Less freedom but you have a guidance for the solution
  • Consequence: introduction of further levels of abstraction for a well-structured development of web apps.
  1. Model → menages data
  1. View → Handles interaction with the user
  1. Controller → coordinates interactions

Template System & Engines

Servlets cannot be easily maintained because of the tight coupling of presentation (HTML) and business logic (in Java).

  • Proposed solution: adoption of a server-side web template system, with templates in HTML, and logic embedded by using special tags.
  • Such templates have to be processed by a template engine, getting to the actual dynamic content.

The Template Engine is in charge of analyzing the “placeholder elements” in the template.

  • getting on the final elements via a collection in the form of a database
  • Not just for web content

Enterprise Applications

Use of plain objects in an enterprise app shows some problems:

  1. No deployment transparency → depends on the way the objects is developed on a particular platform
  1. Implicit dependencies (must be made explicit) → depends on other classes, but these dependencies are implicit

Solution: from concept of object → component

  • Provided/required interfaces: contract between different components
  • Need to support the exploitation of components → a new component to do that

The programmer must focus on business logic, without spending time on distributed computing issues.

Application Server

  • Architectural support to separation of concerns → Container pattern to manage components
  • Middleware solution: Application server
    • An Application Server provides a set of middleware services for web applications, abstracting away the complexities of interacting with the operating system, databases, and other system-level resources.

EJB Container → Enterprise Java Bean

  • It handles EJBs that are in charge of supporting the business logic
  • dealing with data usually present in DB

The Spring Framework

Modular framework to support Java enterprise applications, relying on containers and modules to provide assorted functionalities.

  • Idea: “providing a formalized means of composing disparate components into a fully working application.”
  • Support to JEE features is present as well (in “Context”).

Provide a different, more flexible way to organize an enterprise application

  • deal with every type of applications, not just web-app

Spring has been structured according to several design patterns, such as Factory (no call to new) and Inversion of Control (IoC).

  • IoC is used/provided in the core containers.
    • With IoC, it is up to the framework to call the custom code.
    • Can be specified via Java Annotations or using configuration files
    • You don’t write the complete control flow, but just the components. It’s up to the container to apply the required control flow
  • The configuration and lifecycle management of application Java objects
    is typically done via Dependency Injection (DI).
    • With DI, an object/function receives (by the external container) other objects/functions that it requires: no need to create them internally.
    • DI aims to separate the concerns of constructing objects and using them → not responsability of the programmer to specify what is needed, the middleware will take care of that
    • done via Java Annotations

App development in Spring is “POJO Based”: no specific constraint is posed over Java classes, so just a servlet container is needed, nothing more complex.

  • POJO (Plain Old Java Object) refers to an ordinary class, not required to implement standard interfaces, extend standard classes, etc.
    • for JEE I have a lot of constraints like EJB containers
  • Highly modular: any application can use some modules, and ignore the rest.
  • Annotations: convenient way to specify the roles of the used components

The objects managed by a Spring IoC Container (according to configuration information) are called beans → singleton by default

  1. @Beam → a method-level annotation to specify that the object returned by
    such a method must be handled as a bean
  1. @Component → used to mark a class as a component (bean), that can be specified better with:
    1. @Controller - bean responsible to handle user requests
    1. @Service - bean that holds business logic (provides a service)
    1. @Repository - for DAO classes or similar, with access to data repos.

Spring MVC → web apps according to the Model-View-Controller pattern

As other web frameworks, it uses the front controller pattern:

  • A central Servlet, the DispatcherServlet, provides a common algorithm for request processing
  • The actual work is performed by configurable delegate components:
    • first a controller is chosen to create the model and specify the view
    • then the specific view is used for the response rendering.

    Approach flexible enough to support diverse workflows.

Whenever an incoming REQ is passed to DispatcherServlet:

  1. A HandlerMapping bean is used to determine what specific controller bean to use for this request
  1. The chosen called controller (handler) creates the model and returns indications on what view to use
  1. A ViewResolver bean, given the name returned by the controller, determines the actual View to be used
  1. The chosen View takes care of rendering the passed model

Such beans belong to a specific WebApplicationContext

Spring Boot

Developing Spring applications is challenging because of:

  1. Need for extensive configuration (via annotations/XML etc.)
  1. Complex handling of dependencies (with many modules)

Possible solution: through the “Convention over configuration” principle

  • Idea: take an “opinionated view” of Spring → Spring Boot
    • Simplified configuration
    • Embedded web servers (stand-alone apps, no deployment issues)
    • Off-the-shelf templates for different types of apps

In Spring Boot, we have an “entry-point” class with the “main” method → it must be annotated with @SpringBootApplication, which auto-adds:

  1. @Configuration: Tags the class as a source of bean definitions for the application context.
  1. @EnableAutoConfiguration: Tells Spring Boot to start adding beans based on classpath settings, etc.. For example, if spring-webmvc is on the classpath, this app is set as as a web app, activating the relative behaviors, such as setting up a DispatcherServlet.
  1. @ComponentScan: Tells Spring to look for other components, configurations, etc.

The main() method typically uses Spring Boot’s SpringApplication.run() method to launch the application.

Indirect Communication: JMS

JMS → Jakarta Messaging System

  • Another type of communication called indirect communication
  • It’s up to the indermediator to hadle these messages


MOM (Message Oriented Middleware) is an infrastructure to support indirect and asynchronous communication across components of a distributed application.

  • It makes transparent the networking and communication protocol details, addressing HW/SW heterogeneity → use of msg brokers.
    • Asynchronicity - via message queuing
    • [Intelligent] [Routing] - different routing specifications
    • [Msg Transformation] - via specific tools

Message-oriented technologies rely on an intermediary component: senders may ignore many details about receivers (even identities!).

This is an approach suitable to integrate heterogeneous systems.

Models:

  1. Point-to-point (message queues)
  1. Publish-subscribe (topics)

Point-to-Point Messaging

  • More senders-receiver with possibly shared connections.
  • No hypotheses on the order that msgs are consumed

Publish/Subscribe Messaging

JMS Programming Objects

Objects used to implement JMS messaging:

  • connection factory → create connections
  • connection - comm. channel to the broker
  • session - client/broker conversation
  • producer - obj to send msgs to a destination
  • consumer - obj to get msgs from a destination
  • message - made of header, properties, body
  • destination - represents phys. dest.

JMS Administered Objects (pre-configured JMS objects, that sympify simplify the configuration and management of the app) → administered objects

  1. Connection factories to brokers
  1. Destinations to preconfigured places like queue

Are typically created by Administration tools on the Application Server

  • The clients look up the connection factories and destinations in the JNDI registry to establish communication with the message broker.

Their use in JMS is possible through JNDI (Java Naming and Directory Interface) lookup of the corresponding “administered objects”

  • Message Producer (ClientA):
    • Uses the JMS API to send messages to the broker.
    • First, it performs a JNDI lookup to retrieve the required administered objects (e.g., the connection factory and destination).
  • Message Consumer (ClientC):
    • Retrieves administered objects via JNDI.
    • Uses the JMS API to consume messages from the broker.

  • Message Broker:
    • The central component that routes messages between producers and consumers. It has physical destinations (like queues or topics) where messages are stored temporarily.
  • Object Store:
    • A storage system (or registry) that holds the administered objects. The administrator uses tools to configure these objects and store them here

Enterprise Java Bean (EJB)

EJB is a server-side component that encapsulates the business logic of an application.

  • The EJB container is responsible for managing them, and it provides system-level services to enterprise beans
  • Reusability: new applications can be built from existing EJBs.

Types

  1. Sessions Bean (not persistent in HDD)
    1. stateful → The client holds a reference to the session bean instance, which allows the client to invoke methods on the bean mantaining the state
    1. stateless → Stateless Session Beans are pooled by the container, meaning the EJB container can reuse instances of the bean to serve different clients
      1. Offer better scalability for apps with a large number of clients
      1. Typically, an app requires fewer stateless session beans than stateful session beans to support the same number of clients
    1. singleton → unique, shared across the application
      1. a singleton session bean is accessed concurrently by clients
      1. Singleton session beans maintain their state between client invocations, but are not required to maintain their state across server crashes or shutdowns
      1. Singleton session beans can implement web service endpoints.
  1. Message Driven Beans → business objects whose execution is triggered by messages instead of by method calls

Session EJBs may implement a local/remote interface.

  • The interface represents the contract with the client, and it is usually defined independently of the EJB implementation.
@Local  @Remote
@Stateless  @Stateful
