JVM Runtime Data Area

  • Distrinct parts to host Bytecode, Objects and Stacks for Threads

Class Area

  • shared among all threads → holds class-level data of each .class files
  • Runtime Constant Pool (similar to a symbol table)
  • code for methods and constructors
  • field and method data (just references) + static variables

Heap

Shared among all threads

  • contains the representations of all the instances of all the classes handled in the program as well as arrays
  • It is subject to garbage collection
  • also String Constant Pool (string with same literal will refer to that pool) and string interning (force a string to be a literal)

Stack Area

Each thread has its own stack

  • any function call is menaged using a Frame in the pertinent stack
    • array of local variables
    • a ref to runtime const pool
    • its operand stack (JVM is a stack machine)

Thread Termination

Some early methods (deprecated):

  • stop() → may lead inconsistencies because releases all the locked monitors
  • suspend/resume() → suspend a thread in the critical section and another thread that could resume it cannot reach that part → Dead-Lock Prone

Cooperative mechanism based on the inter-thread interruption

  • interrupt flag → can be setted by another thread invoking the interrupt() method
  • Thread.interrupted() → check its own interrupted flag and clear it
  • isInterrupted()→ check the flag of any thread without clear it
    • A thread that becomes aware of being interrupted is programmed to perform cleanup

What if an inter-thread interruption is performed to a blocked thread? It depends...

  • If it is blocked on an explicit waiting operation, an InterruptedException awakes the target thread (and clears the flag).
  • If it is blocked on accessing a lock/monitor, it is not awaken; with explicit locks, lockInterruptibly() can also be used.

InterruptedException should be handled in this way:

  1. re-throw the exception after a possible re-wrapping
  1. restore interrupted flag → to keep memory of the occurence of the interruption event

Thread Pooling and the Executor Framework

Thread → sequence of instruction that can be executed independently of others in the same programs, typically under the control of a scheduler

Task → actions to be carried out (don’t worry about who carry out the pomeration)

  • Server request trigger tasks that could be executed by a single thread or by more than one
  • defined via a Runnable class

A task can be defined via a Runnable class

public interface Executor {
		void execute(Runnable command);
}
class DirectExecutor implements Executor {
	public void execute(Runnable mytask) {
		mytask.run();
	}
}

Performance Penalties: from wasting time in menagement actions

  • contet switches → determine the cache flush
  • lock contention → thread wait time
  • Memory Synchronization → threads may need to see last updates
    • lock elision from the JVM to remove unnecessary synch
    • Can be specified also on methods → but acquire the class level lock (so every method in the class cannot execute on the same time)
synchronized (new Object()) {  // useless because there is no mutual excl (lock elision)
	foo();
}
  • Object act as a locker, that is hold just by one thread at the time

Thread Pooling

Keep some threads ready to execute upcoming tasks and, upon completition of each exection, make the thread available again for another task

Executors can be designed to implement an execution policy

  • If I need to synch processes I need something more complex
  • They manage thread pools

Some factory methods for Executors

  • newFixedThreadPool(int n) creates a pool of n threads, with fixed size
  • newCachedThreadPool() provides a thread pool that creates new threads as needed, but will reuse previously constructed threads when they are available
  • newWorkStealingPool(int parallelism) creates a pool with dynamically managed threads, able to handle the specified level of parallelism; the task execution order does not necessarily reflect the order of submission

To shout down an Executor I have some options:

  • shutdown() starts the shutdown procedure; previously submitted tasks are completed, and no new task will be accepted.
  • shutdownNow() - only currently executing tasks are completed.
  • Check state by using isShutdown(); isTerminated() checks if all tasks have been terminated.
  • Methods above are not-blocking; to wait for completion of all tasks, call awaitTermination()

Synchronizers

Latches

A latch is aimed at making a group of thread wait until it reaches its terminal state → the couter reach 0.

  • countDown(), getCount(), await() to wait that the latch open → when arrives to 0
  • similar to join but serves to synch more threads together

Barriers

A thread that gets to the barrier waits for all the others to come. As the last arrive, all threads are released

  • can be reused (latches no)
  • just call await()

Phasers

Is a sophisticated version of a barrier/latch

  • reusable
  • Differently from barrier the number of parties can change over time

Semaphores

Aimed to control the number of access to a resource → can be used for mutual exclusion

  • max number of permit is decided at initialization time
  • acquire() is used to get a permit
  • release()

Exchangers

two threads wait for each other at a synch point, and then swap objects

Thread Safe Data Structures

Syncronized Collections

  • make all the methods of the collection syncronized
  • It can be done in a systematic way uning the decorator pattern (wrapper object)
// This could be dangerous in multi-threaded code:
if (collection.isEmpty()) {
    collection.add(item); // Another thread might have added 
}                         // items between these two lines!
  • each operation in mutual exclusion with a single lock for all the ops in the class (reduced concurrency)
  • Specific static factory methods in java.util.Collections
Collection<T> c = Collections.synchronizedCollection(myCol);

synchronized(c) {
			 for (T item : c) foo(item);   // a lot of synchronization overhead 
}

Concurrent Collection

  • A “synchronized” collection shows poor performance under high contention.
    • Solution: reduction of synchronization overhead, applying any possible trick (reduce the part of code to be run synchronized). “Concurrent” versions of “Synchronized” collections have been developed: e.g., ConcurrentHashMap is an improvement of SynchronizedMap

ConcurrentHashMap

It implements the ConcurrentMap<K,V> interface, which includes also atomic read+write operations.

  • boolean replace(K key, V oldValue, V newValue) - equivalent to the atomic execution of:
if (map.containsKey(key) && Objects.equals(map.get(key), oldValue)) { // Null safe equal
		map.put(key, newValue);
		return true;
} else return false;

Iterating over concurrent collections

Iterating over a concurrent collection is risky:

  • other threads may access the data structure at the same time!

The same problems arise with “for-each” loops, which are compiled to the corresponding iterator-based form.

  • It is necessary specifying new semantics for a concurrent iterator, so to fully describe its behavior in case of possible interferences.

Fail-fast Iterator

  • Provided by most of non-concurrent collections
  • Used to traverse the actual collection: no modification to the collection is allowed.
  • As soon as a modification is detected (on a best effort basis), ConcurrentModificationException is thrown.
  • Modifications are detected by inspecting specific counters.
    • Note: it is safe to remove an element via the remove() method of the iterator - not the remove() of the collection!

Weakly-consistent Iterators

Called also “fail safe.” Provided by most of concurrent collections.

  • may proceed concurrently with other operations
  • will never throw ConcurrentModificationException
  • are guaranteed to traverse elements as they existed upon construction exactly once, and may (but are not guaranteed to) reflect any modifications subsequent to construction

Snapshot Iterators

Used with copy-on-write collections like CopyOnWriteArrayList.

  • The iterator provides a snapshot of the state of the collection when the iterator was constructed.
  • No synchronization is needed while traversing the iterator.
  • The iterator does NOT support the remove() method.
  • In such collections, all “mutative operations” are implemented by making a fresh copy of the underlying data structure, i.e. Copy-On-Write (COW).

Blocking Queues

High-performance, thread-safe version of bounded buffer, designed according to the BlockingQueue<E> interface.

  • Methods are present to support insertion, extraction, and inspection in different fashions (blocking, throwing exceptions, polled, timed)
  • Blocking queues support the producers/consumers pattern. Blocking queues make resource management more reliable. Impl. of the classic bounded buffer: ArrayBlockingQueue<E>
