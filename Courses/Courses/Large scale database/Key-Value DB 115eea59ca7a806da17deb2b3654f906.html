Key-Value DB

  • Keys must be unique within the namespace defined in each specific bucket
  • There is no need for tables if we do not need groups of related attributes.
  • Simplicity (no schema or data types, easy to add new buckets), speed (ram → LRU replacement) and scalability (easy to add nodes in distributed system)

We define a namespace, ie. a bucket, which is a collection of keys and values. In each bucket, so in each namespace, all keys are unique. Keys can repeat in different namespaces/buckets

  • If we don’t need features of the relational models (eg. joining)
  • A lot simpler to change the structure of the db rather than the relational counterpart, since I would need to destroy and recreate the table

Master-Slave (data) replication

  • The master is a server that accepts write and read requests and update the data to all the slaves that have the request shard
  • The slaves may only respond to read requests (writes only the master)
  • This architecture is particularly suitable for applications with a growing demand for read operations
  • There is no need to coordinate write operations or resolve conflicts between multiple servers accepting writes.
  • if the master fails, the cluster cannot accept writes.

If a number of slave servers do not receive a message from the master within some period of time, the slaves may determine the master has failed.

  • The slaves initiate a protocol to promote one of the slaves as a new master.

Masterless replication

Use case: applications in which the number of writes may increase and achieve peaks! Example: the website which sells ticket of concerts.

  • There is not a single server that has the master copy of updated data.
  • Each node is in charge of helping its neighbors.

The ring structure is an abstraction. Usually, in a data center, all the servers are connected to a single network hub and are able to communicate with each other.

  • Each time there is a write operation to one of the servers, it replicates that change to the three other servers holding its replica (we consider 4 data replicas).
  • Each server replicates to its two neighbors and to the server two links ahead

Clusters

  • mostly independent clusters (loosly coupled)
  • each server is responsible for its own partitions and periodically send messagges to other nodes saying that it is still working, otherwise take over its work

To maintain strict consistency I need W+R>NW+R>NW+R>N﻿

  • N: number of replicas
  • W: number of write to be performed now, the others later
  • R: number of read to make before finish the operation

The higher number of replicas, the less likely we will loose data, the lower the performance of the systems (in terms of response time).

  • A low number of replicas may be used whenever data is easily regenerated and reloaded.

Naming convention for keys

  • Use meaningful and unambiguous naming components, such as 'cust' for customer or 'inv' for inventory.
  • Use range-based components when you would like to retrieve ranges of values. Ranges include dates or integer counters.
  • Use a common delimiter when appending components to make a key (e.g. the ‘:’ delimiter )
  • Keep keys as short as possible without sacrificing the other characteristics mentioned in this list.

Limitation

  • The only way to look up values is by key. Some DBMSs for key-value DB offer APIs that support common search features, such as wildcard searches, proximity searches, range searches, and Boolean operators. Search functions return a set of keys that have associated values that satisfy the search criteria.
  • Key-value databases may not support range queries. Some DBMSs (ordered KV databases) keeps a sorted structure that allows for range queries and/or support secondary indexes and some text search.
  • There is no standard query language comparable to SQL for relational databases
