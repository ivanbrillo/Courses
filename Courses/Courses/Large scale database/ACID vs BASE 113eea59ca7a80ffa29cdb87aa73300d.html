ACID vs BASE

One of the best way to scale a relational db:

  1. Sharding that is a partitioning technique that splits a large database into smaller, more manageable pieces called shards. Each shard is stored on a separate database server instance.
    1. allow simple scale-out technique
  1. Caching that involves storing frequently accessed data in a high-speed storage layer to reduce the load on the database.
  1. Replication that creates and maintains copies of the database across multiple servers in order to enchance data availability and fault tolerance

These aspects bring some problems:

  • How to propagate changes inside all the replicas to mantain consistency? We are losing availability, because we need to wait all the nodes. We need to find a balance between consistency and availability.
  • ACID transactions against multiple shards are not practical (two-phase commit)

Consistency vs Integrity

Consistency and integrity of a database describe a state in which the stored data does not contradict itself.

  1. Data Consistency ensures that a transaction can only bring the database from one valid state to another → no logic contraddiction
    1. It's a logical property of the DB, independent of the actual data. A DB that reported employee Joe Shmoe's department as Sales but that didn't list Joe Shmoe among the employees in the Sales department would be inconsistent
  1. Data integrity constraints to ensure that data consistency is maintained for all insert and update operations.
    1. refers to the accuracy and completeness of data throughout its life cycle. It is maintained via integrity constraints (eg. for all update or insert)
    1. A DB that reported jOe SaleS to be a member of the Shmoe department would lack integrity. jOe SaleS isn't a valid employee name and Shmoe isn't a valid department. That's not logically invalid, but it is invalid relative to the rules that govern data content.

Consistency First: Two-Phase Commit

failures of the operating system, voltage drops, disks break down.

  • the two-phase commit is a transaction!
  • You can have consistent data, but transactions will require longer times to execute than if you did not have those requirements
  • While the two-phase commit is executing, other queries to the data are blocked. → unavailability in favor of consistency

Availability First

In this kind of applications (real time, e-commerce), the availability of the system and its fast response is more important than having consistent data on the different servers.

  • The data on the backup server would be inconsistent with data on the primary server if the primary server failed prior to updating the backup server.
  • Longer latency could lead to less purchases or requests
  • eventual consistency (cannot be used for banking)

Network Partition

The system has two choices after a failure that partition the system:

  1. either show each user a different view of the data (availability but not consistency)
  1. or shut down one of the partitions and disconnect one of the users (consistency but not availability).

The CAP Theorem (Brewer’s theorem)

DIstributed databases can ensure simultaneously at maximum two of the following features:

  1. Consistency: presence of consistent copies of data in different servers
  1. Availability: providing a response to any query
  1. Partition protection: Failures of individual nodes or connections between nodes do not impact the system as a whole.

CA solution

Since a CA system prioritizes both Consistency (C) and Availability (A), it cannot sacrifice either property in the presence of a network partition → Therefore, a CA system cannot support Partition tolerance (P)

Single Site cluster, therefore all nodes are always in contact

  • Use cases: Banking and Finance application, system which must have transaction e.g. connected to RDBMS.
  • Total consistency can affect performance (latency).

AP solution

System is still available under partitioning, but some of the data returned may be inaccurate (eventual consistency) → masterless system

  • Availability is also a compelling option when the system needs to continue to function in spite of external errors.
  • Use cases: shopping carts, News publishing CMS, etc.
  • Notice that this solution may return the most recent version of the data you have, which could be stale. Indeed, this system state will also accept writes that can be processed later when the partition is resolved.

CP solution

As suitable for application which require consistency, but also partition tolerance, while somewhat long response times are acceptable (Bank ATMs).

  • Master application where all the writes are asked just on one node and this ensure consistency, the partition tolerance part is guaranteed by replacement solution (meanwhile no A)

BASE properties of NoSQL DB

  • BA (basically available): handle partial failure to preserve availability, thanks to data replication
  • S (soft state): the state of the system may change over time, even without user input, because of eventual synchronization between distributed nodes.
  • E (eventually consistent): data in all nodes will converge to a consistent state

The latency Issue

  1. If I want high availability, a requirement of modern applications, I need replicas.
  1. If i implement replicas i must take care about the consistency
  1. The stronger the consistency the higher the latency.

Types of Eventual Consistency

  • Read-Your-Writes Consistency ensures that once a user has updated a record, all of his/her reads of that record will return the updated value.
  • Session consistency ensures “read-your-writes consistency” during a session. If the user ends a session and starts another session with the same DBMS, there is no guarantee the server will “remember” the writes made by the user in the previous session.
  • Monotonic read consistency once a client has observed a particular value for a piece of data, it will never see an earlier value of that data in subsequent reads.
  • Monotonic write consistency ensures that if a user makes several update commands, they will be executed in the order he/she issued them.
  • If an operation causally depends on a preceding operation, there is a causal relationship between the operations. Causal consistency ensures that users will observe results that are consistent with the causal relationships.
