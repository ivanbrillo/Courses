Database Revolutions

Database is an organized collection of data (libraries/dictionaries can be considered the first databases)

First Database Revolution (1960s)

Requiring every application to write its own data handling code was clearly a productivity issue: complex optimization and concurrent access

  • It became desirable to externalize database handling logic from the application in a separate
    code base (DBMS that provide data schema and access path to the data)
  • The first kind of DBMS used navigational models, wheredata was organized using hierarchical or network structures, and relationships were explicitly defined through pointers or links.
    • not far from nosql dbms
  • Two major model of DBMS: network model and hierarchical model

The issues were:

  • Only queries that could be anticipated during the initial design phase were possible. It was extremely difficult to add new data elements to an existing system → declarative vs procedural
  • Lack of theory behind
  • CRUD (Create, Read, Update, Delete) operations oriented → complex analytic queries required
    hard coding

Second Database Revolution (1970s) - Client-Server ERA

The lack of theory behind BDMS led to the pubblication of “A Relational Model of Data for Large Shared Data Banks, 1970”. The key concepts were:

  1. Tuples, an unordered set of attributes
  1. Relations, that are a collections of dinstrict tuples
  1. Constraints, which enforce consistency of the database
  1. Operations such as joins and projections

Transaction Model (late 70s) - ACID

It provide rules to handle concurrent data access, that requires to mantain consistency and integrity

  1. Atomic: or all statements are applied or none to the db
    • The transaction is indivisible - either all the statements in the transaction are applied to the database or none are
  1. Consistent: db stays in a consistent state before and after a transaction
  1. Isolated: While multiple transactions can be executed by one or more users simultaneously, one transaction should not see the effects of other in-progress transactions.
  1. Durable: Once a transaction is saved to the database, its changes are expected to persist even if there is a failure of operating system or hardware.

OOP Failed Revolution

The object-oriented programming revolution set the stage for the first serious challenge to the relational database, which came along in the mid-1990s.

  • When an object was stored into or retrieved from a relational database, multiple SQL operations would be required to convert from the object-oriented representation to the relational representation

OODBMS

An OODBMS would store program objects directly without normalization, and would allow applications to load and store their objects easily

  • resamble the networks models
  • failed to gain market share

ORM (Object-Relational Mapping)

Frameworks that automated the most tedious aspects of the translation between the two paradigms: objects and relational database tables.

  • Can introduce performance overhead

Third Database Revolution (2000s) - Web Scale Application

The difference in application architectures between the client-server era and the era of massive web-scale applications created pressures on the relational database that could not be relieved through incremental innovation.

  • RDBMS was inadequate to deal with the volumes and velocity of the data confronting Google
  • hard to modify the structure of existing data,
  • hard to deploy to multiple servers and guarantees ACID transactions on the massive web-scale applications
  • performace issues

New needs that RDBMS cannot offer:

  1. Scalability → turn on and off servers based on requests
  1. Flexibility → Items of the same type may also have different descriptions and missing values (no schema in advance → no normalization)
  1. Availability → deploy the system on more servers

NoSQL

NoSQL is the acronym of Not Only SQL

  • ACID transactions may be not supported by NoSQL databases.
  • reject constraints of relational models (consistency and shemas)
