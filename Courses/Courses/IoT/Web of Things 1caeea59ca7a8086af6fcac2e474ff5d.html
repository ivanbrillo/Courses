Service Oriented Architectures

Cloud technologies were based on this architecture

  • SOA is to take a large apllication and brake down all it’s functionalities into services, that runs independently from the others
  • This ensures expandability, reutilization, maintainability since the services are loosly coupled

Service are aware of each other through the use of service descriptions

  • published inside a broker
  • Name (adress) of the service and data expected (and returned)

Services exhanged through messages

World Wide Web

Origins (1989, CERN)

  • A system to share research documents

The Web today

  • Now it provides multimedia data and services

Three Components

  1. Identification of resources → Uniform Resource Identifier (URI) for identifying an abstract or physical resource
    • Resource: any entity that has an identity (document, image, service, …)
    • Uniform: different types of resources identifiend in the same context, extensible
    • Identifier: string with restricted syntax
  1. Data Exchange → Hyper-Text Transfer Protocol (HTTP)
    • Application level protocol for communication
  1. Data Encoding → Hyper-Text Markup Language (HTML) to encode data in documents
    • Not good for application data encoding, but just for web pages for web-browsers → XML (generalization of HTML)
      • Any thype of data can be encoded
      • extensible since the tag set is not prespecified

Web Services for IoT

Provide data (sensing) and actuating capabilities to client applications as IoT web Services

  • The devices are the producers, each of them is associated with an URI
  • They implements the HTTP protocols and XML encoding

Soap

SOAP (Simple Object Access Protocol) light protocol to exchange data in a distributed environment

  • XML-based messaging framework
  • SOAP messages can be exchanged over any protocol (e.g., HTTP, SMTP)
  • SOAP messages originate at an initial SOAP sender and are sent to an ultimate SOAP receiver via zero or more SOAP intermediaries

WSDL (Web Services Description Language): XML grammar for describing network services as collections of communication endpoints capable of exchanging messages

  • Service are aware of each other through the use of service descriptions
    • name of services and data expected and returned
    • written in WSDL, hosted by a broker-service directory
  • Services exchange information through messages with SOAP structure

In IoT I can use it for:

  1. Machine-to-Machine (M2M) interactions (between devices)
  1. Application-to-Machine interactions (device with cloud)

Too much overhead for IoT devices → REST

  • REST is a revisitation of SOA in order to ensure an architecture that is more lightweight, more simple and with a reduced set of functionalities

RESTful

REST (Representation State Transfer) → resource orieted architecture for distributed system

  • Client applications do not invoke services, but interacts with resources
  • Interactions is realized by four standart actions (CRUD) on resources: create, read, update and delete
  • Web centric approach, HTTP methods associated to CRUD actions
    • Can still use XML, but the additional overhead added by SOAP is removed
  • Reources are identified with URIs

They are the predominand approach for the Web of things

  • less overhead, less parsing complexity, tighter integration with HTTP, stateless, higher flexibility

However devices that host resources are energy cotrained and connected to constrained networks:

  1. HTTP is stable, but high data overhead → introduce new protocol called CoAP
  1. XML is flexible, but high parsing overhead → find alternative data encoding (text, JSON)
