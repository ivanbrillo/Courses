Introduction and Smart Objects

Smart Object: any real-world object empowered with

  1. Communication capabilities
  1. Computing capabilities
  1. Sensing/Actuating capabilities → physical word interaction
  1. Power Source → battery-solar panel

Instrumenting Device: low cost device embedded to the object, providing computing, power, communication and sensing/actuators.

  • RFID readers

When you integrate an instrumenting device into a physical object, that object transforms into a smart object capable of interacting with its environment and other systems

  • Smartphones are instrumenting devices (lot of sensors)

Not all necessary, in a RFID we need only memory and the communication module

Different smart objects can cooperate to perform a specific task with Wireless/Wired communication → Smart Object Network

Smart Environment → place where human activities are assisted and supported by ICT (information and communication technologies) via smart objects

  • most of the place where we live or spend time are smart, or can be made smart
  • smart home or buildings

Buildings, Factories, Energy Plants are connected via a smart grid, exchanging power and data

Smart Mobility → made of sensor deployed at the main entrance of the city, allows to take timely and appropriate decision (eg. semaphor)

Smart Factory → Real-time networking of human beings, machines, and smart objects for intelligent factory management

Lots of smart sensor and actuators, wirelessly connected

IPv6 offers:

  1. Interoperability: independece of underlying technologies (MAC layer)
  1. Scalability: unique adressing and self configuration
    • lot of addresses
    • no DHCP needed → auto configuration
  1. End-to-End: no multi-protocol intermediate gateways that have security holes and are expensive
    • no NAT protocol needed anymore as IPv4

IoT protocol defined by IETF

Protocols that have been chosen by the IETF (Internet Engineering Task Force) to enable communication between constrained devices in IoT systems.

  • Data Link layer: the IETF assumes the IEE 802.15.4 MAC protocol, which has been designed for low-power communications.
    • Small frames, the max payload is 127 bytes.
  • Adaptation Layer to allow the transmission of IPv6 datagram on a IEEE 802.15.4 frame → 6LowPAN
    • Not present in the default architecture, because IPv6 minimum len is 1280 bytes
    • compress/translate the IPv6 header (since the max payload is 127 bytes, we want to compress to the max possible)
    • how fragmentation can be performed (IPv6 standard payload is 65.535 byte).
  • Network layer: IPv6 in order to have a protocol that guarantees interoperability, scalability and QoS.
  • Transport layer: UDP, because TCP it requires a lot of resources (like memory and computational complexity)
  • Application layer: The Constrained Application Protocol (CoAP) fulfill IoT devices needs. It’s a simplified version of HTTP with specific features for the IoT (since they have lack of resources to use HTTP) → less memory usages then HTTP
    • RPL instead is the Routing Protocol for multi-hop communication. It collects information on the network topology, computes the multi-hop routes and populates the routing tables of each node.
    • Multihop is used since the trasmission range of devices is limited (low power)

C2TC Cloud to things continuum

The C2TC continuum represents the seamless integration of computing resources from centralized cloud infrastructure to distributed edge devices and IoT endpoints. Three key layers:

  1. Cloud computing handles computationally intensive tasks that require significant processing power and storage, leveraging centralized data centers for heavy workloads.
  1. Edge computing provides low-latency support for delay-sensitive applications by processing data closer to its source, enhancing privacy and security while reducing data transfer requirements.
  1. AIoT (Artificial Intelligence of Things) extends AI capabilities throughout the entire continuum, enabling intelligent decision-making not just at centralized locations but distributed across edge devices and IoT sensors for real-time, context-aware responses.

Sustainability

  1. Batteryless IoT → collect energy from external sources
    • Coordination of a network of batteryless devices not trivial since they could be out of sync → generally doesn’t communicate with other nodes
  1. Energy-Aware Task Offloading → algorithms that dynamically decide where process tasks (cloud, edge, or device) based on energy consumption and latency requirements
  1. Energy-Aware Resource Allocation → algorithms that prioritize energy efficiency, such as scaling down resource usage during low-demand periods

Smart Objects

  1. Passive sensors are sensors that stores some information, reachable by some readers. They don’t need any source power
    • RFID (to identify an object) or QR-code
    • Library infos, ticketing, animal tagging, augmented reality in smart city (points of interests), …
  1. Semi-passive sensors, also called data loggers, they need limited amount of energy and memory to measure and store some physical information, so they are powered by a battery
    • No need for communication
    • temperature monitoring, shock tracking
  1. Active sensors: sensors battery powered, with computational and communication capabilities
    • Beacons are hardware transmitters that emit periodic signals using Bluetooth Low Energy (BLE)
      • Beacons enable devices to perform actions when in proximity based on the received signal (periodic)
    • Sensor nodes

Beacon for Advertisement messages (ADV)

The ADV message is received by a smartphone and forwarded to a server

  • The server localizes the device (user) and sends appropriate information to the smartphone
  • Small packet trasmitetd at intervals → one way communication
  • Can be used in localization in buildings, coupons delivered via becons to customer phone, locate museum artworks, indoor navigation

Lifetime up to 3 years with a single coin cell battery thanks to BLE

  • Traditional Bluetooth is better for more complex applications requiring consistent communication and higher throughput

Advertisement messages consist of four main pieces of information:

  • UUID (Universal Unique IDentifier): 16 byte string used to differentiate a large group of related Beacons.
    • Typically represented with 32 hex digits
  • Major: 2-byte string distinguishing a subset of Beacons within the larger group
  • Minor: 2-byte string used to identify individual Beacons
  • Tx Power: Used to determine the distance from the beacon.
    • TX power is defined as the strength of the signal at exactly 1 meter from the device.
    • This has to be calibrated and hardcoded in advance.
    • Devices can then use this as a baseline to give a rough distance estimate

Sensor Node architecture

They not only measure quantities, but also process them and are capable of transmitting the collected information.

  • Reliability: Although an individual node may fail, we require long-lasting applications. We do not have an on field recovery mechanism, except for automatic rebooting

Examples: the smartphone is a very special sensor node since it has a lot of sensors, but it’s easy to recharge so power management is not a big issue

  • PCs, smartphones operate mainly based on user input, instead sensor nodes act based on external conditions

TinyOS

  • Component based architecture
    • unused services are excluded from the application
    • provide an abstraction (expose an interface) over the hardware to the programmer
    • Frames are the private variables of the component
  • Command is a service request to a component
    • non-blocking
    • Rather than performing a computation immediately, commands and event handlers may post a task, a function executed by the TinyOS scheduler at a later time.
  • Tasks are an explicit entity in the language. A program submits a task to the scheduler for execution with the post operator
    • The scheduler can execute tasks in any order, but must obey the run-to-completion rule
    • They are not pre-empted by other task, but only by interrupts/messages
  • Event when a command is completed (message or interrupt)
    • Event based concurrency

It uses nesC language → extention to C that provides interfaces

  • Provides also a simulator (TOSSIM) in order to simplify the code debugging phase
