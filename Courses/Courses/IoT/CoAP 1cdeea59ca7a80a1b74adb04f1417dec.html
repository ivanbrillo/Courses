CoAP

COstrained Application Protocol (2014)

  • Web protocol for constrained environments (LLNs), especially considering M2M applications

Features:

  • UDP transport protocol (vs TCP in HTTP)
  • Low header overhead and parsing complexity → binary version format and fixed length (can use masks)
  • proxy and caching capabilities from HTTP
  • stateless HTTP mapping from CRUD operations (StateLess)
  • support for multicast communication
  • support for the discovery of resources

Goal: realize an application protocol for web services (common with HTTP) but optimized for M2M applications

Interaction Model

Interaction model optimized for contrained environments:

  • Request/Response Layer: Handles the exchange of requests and responses between applications and servers (packing and unpacking)
  • Asynchronous Message Layer: Manages message reliability over unreliable transports like UDP
    • Optional reliability is introduced at the application layer through retransmission and acknowledgment

Define 4 different type of messages:

  1. Confirmable (CON) → requires ack
  1. Non-confirmable (NON) → do not requires ack (asynchronous)
  1. Acknowledgement (ACK)
  1. Reset (RST)
    • A recipient sends an RST in response to a Confirmable (CON) or Non-Confirmable (NON) message when it received the message, but lacks the necessary state or context to process it properly.
    • Signal what msg has rejected since it will contain the same msg ID

In case optional reliability is enabled only confirmable message are transmitted, meaning that request and responses are sent as confirmable messages.

  • A confirmable message must be acknowledged by the receiver, the sender implements a time-out mechanism to retransmission.
  • If reliability is disabled, request and responses are sent as non-confirmable messages which do not require acknowledgment.

It uses the same methods of HTTP for requests and responses.

  1. Every Request is characterized (as in HTTP) by:
    • Method
    • URI
    • Payload and optional meta-data (CoAP options)
  1. The Response includes:
    • Response Code → specify the outcome
    • Payload and optional meta-data

CoAP is bound to non reliable transport layer (UDP). A lightweight reliability mechanism is needed

  1. Stop&Wait retransmission with exponential back-off (Reliable Trasmission)
    • in order to implement a very simple a congestion control, the exponential back-off is used
    • Adopts a retransmission and acknowledgement managed with a time-out
    1. A reliable trasmission is started by sending a CON msg
    1. The client can respond with an ACK, with a RST msg (both having matched msg ID) or just ignoring it
    1. The sender if nothing arrives can retransmits the CON message at exponentially increasing
      intervals (2s default), until either:
      • it receives an ACK or RST message, or
      • runs out of attempts (4 by default)
  1. Duplicate detection: detection and management of duplicate packets during data transmission is performed by observing the Message ID of the various messages.

Unreliable Trasmission

  1. started with a NON message (eg. regular sensors data), the msg ID is included as well to detect duplications
  • There is no way for the sender to detect if it arrives

Requests are carried in CON or NON messages

  • A Token matches responses to requests
  • No relationship between Tokens and Message IDs

  • If in a CON message: responses may be carried in:
    • the resulting ACK messages (piggy-backed) → syncronous
      • In this case, the request and response share both the same token and the same message ID
    • in a new CON message (separate) → asyncronous
      • same token, different msg IDs
      • Should be adopted if the server use a lot of time to generate the response. Because otherwise, due to the “congestion control”, the 2s expire and after a backoff, messages are sent again and it generated useless traffic
  • If in a NON message: responses are sent in a new NON message
    • same token, different msg IDs

An empty message contains only the header.

  • They are usually used to send ACK without immediate response or RST (often used when receiving an unexpected or unrecognizable message, cannot process it)
  • CON empty message to implement CoAP ping used to check if a specific server is up and running.
    • Send an empty CON message to a server and wait to see if a RST msg is returned

Msg Format

Another significant difference between CoAP and HTTP is the format of the messages.

  • CoAP adopt a binary format to minimize the size of the messages, HTTP instead adopt a text format.
  • The header of the CoAP message is of a fixed size 4 bytes
  • Version: currently 1
  • Type (T): message type (0 CON, 1 NON, 2 ACK, 3 RST)
  • Token Length: 8 bytes at most
  • Code: split into 3-bit class and 5-bit detail (c.dd)
    • Class: request (0), success response (2), client error response (4), server error response (5)
    • Detail: specifies the method (e.g., 0.01 is a GET) or the response code (e.g., 2.04 is 'Created')
    • Special code 0.00 indicates an Empty message
      Code (c.dd)ClassDetailMeaning
      0.01–0.040 (Request)1–4GET, POST, PUT, DELETE
      0.000 (Empty)0Ping / Empty ACK / RST
      2.xx2 (Success Resp)e.g. 01–05Created, Content, etc.
      4.xx4 (Client Error)e.g. 04, 05Not Found, Method Not Allowed
      5.xx5 (Server Error)e.g. 00, 05Internal Error, Not Supported
  • Options (message options, the size can vary over a very wide range)
    • Request URI is split into the Uri-Host, Uri-Port, Uri-Path and Uri-Query Options
      • better parsing and more data efficient (important for constrained devices)
    • coap-URI = "coap:" "//" host [ ":" port ] path [ "?" query ]
    • Allows to specify other options like ETag, If-Match, Max-Age, Content-Format, …

Proxying

CoAP allows (like HTTP) for the introduction of intermediaries.

  • Intermediary: endpoint that can be introduced in the middle between the CoAP client and the origin server, in order to implement some additional functionalities that cannot be implemented on the server or the client.
    • It behaves as client towards the origin server and as server towards the client.
  • Endpoint: any device that implements even partly the CoAP functionalities

One type of intermediary defined in CoAP is the proxy CoAP

  • This proxy is placed here to perform additional functionalities like caching, protocol translation, or security functionalities rejecting unwanted requests
  • Caching is an important functionality, this allows to save bandwidth and energy.

Two proxy types: forward and reverse

Forward Proxy

Performs requests on behalf of the client.

  • Clients issues their request directed to the origin server, this request however is sent by the client to the proxy, this forward proxy receives the request and issues the request to the origin server.

  • The origin server send back a response which is forwarded to the client.
  • The endpoint (the server) is selected by the client since he have to specify to full URI.

In this process, the client is fully aware that a proxy is present on the middle → not transparent

  • In fact, the client has the flexibility to choose whether and which proxy to use for communication in the Proxy-Uri option
  • This configuration is usually exploited when there are some functionalities on proxy, like protocol translation

Reverse Proxy

Satisfies requests on behalf of one or more other server(s).

  • In this case, the proxy is completely transparent to the client.
  • It is installed to provide coverage for a network of sensors or servers, and its purpose is to handle requests on behalf of one or more servers.

The server only exposes the functionalities through the proxy

  • Usually adopted when the architect wants to hide completely the architecture of IoT devices.

Proxy Traslation

One of the functionalities that could be implemented by a proxy is a protocol translation functionality

  • The proxy can implement the Cross-protocol proxy (Cross-Proxy): a proxy that translates between different protocols.

Two different cases:

  1. CoAP-to-HTTP proxy → Is a proxy that is installed on a CoAP network to have the CoAP clients (sensors) interacting with HTTP servers.
  1. HTTP-to-CoAP proxy → Is a proxy that translates HTTP requests into CoAP request, so it can be used to have regular HTTP clients to interact with CoAP servers.

Usually proxy are both of them at the same time, to allow devices that send a request and to receive a response

CoAP Resource Observing

If a client is interested in being indefinetely updated about a resource

  • No continous polling since it leads to high overhead
  • Observation pattern (resemble publisher/subscriber)

    A resource can be observable or not (is optional)

If using polling the temperature could be almost the same, meanwhile the server could send it just when there is a significant change

  1. The first message is a GET request to register to the observable resource
  1. Registration and notifications are correlated by the same token
  1. There is an observe field in order to reorder correctly the msgs

We can specify the pattern that needs to match, in order to receive an update:

  • coap://server/temperature/critical?above=45 is a different resource wrt coap://server/temperature

It’s up to the server expose observable resources that updates the client in a useful way

Consistency between the client view and the actual resource state (latency, msg lost, reordering). The Best effort approach is used:

  1. Updates are sent as soon as possible, but there are no guarantees on strict synchronization.
  1. As many states as possible should be delivered to the client, but some updates may be missed.

Bound the out-of-sync time duration with a maximum age attached to notifications

  • specifies for how long a response can be used before it is considered stale

There is no end-to-end observing concept → proxy could exploit this feature

Discovery

Capability of discovering devices in a network and the resources they expose

Service Discovery

Process to discover CoAP servers in a network

  • Multiast CoAP using the default multicast adress (bouded to the link-local scope)
  • If I want to access and discovery the internet, I need a different protocol

Resource Discovery

Process to discover the resources exposed by a service

There is a resource that must be exposed on all CoAP servers, that is /.well-known/core

  • default entry point for requesting the list of resources hosted by the server
  • CoRELink Format to describe links (resources) hosted by the server
    • Collection of links, each separated by a comma.
    • For each link I have the URI, then list of key-value attrubutes

Attributes:

  • Resource Type (rt): opaque string used to assign an application specific semantic type to a resource
  • Interface Description (if): opaque string used to provide specific interface definition used to interact with the target resource
    • E.g.: the URI of a Web Application Description Language
  • Maximum Size Estimate (sz): an indication of the maximum size of the resource representation
  • Content Format (ct): provides a hint about the Content-Formats this resource returns
  • Observable(obs): a hint indicating that the destination of a link is useful for observation

I could perform some filtering to the default page of well-known. Like filtering for resource names or sensor types

GET /.well-known/core?rt=temperature-c&if=sensor
