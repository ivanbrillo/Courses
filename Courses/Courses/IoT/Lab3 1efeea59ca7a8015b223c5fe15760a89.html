Assumptions on the IPv6 implementation

  1. each node has a single interface
  1. each interface can have up to UIP_CONF_NETIF_MAX_ADDRESSES unicast IPv6 addresses
    including its link-local address
    • default value is 3

The prefix (0xfd00) may also be 0xfe80, depending if we refer to a global or a link local IPv6 address

Each Contiki node must be configured with at least one IPv6 address before it can send or receive IPv6 packets.

  • You typically construct a full 128-bit address from a chosen prefix and the node’s link-layer address
  • embed the 64-bit Interface Identifier (IID) based on its MAC into the lower half of that address, and
  • register it with the IPv6 interface 
  uip_ipaddr_t ipaddr;
  
  uip_ip6addr(&ipaddr, 0xfd00,0,0,0,0,0,0,0);    /* 1. Build prefix */
  uip_ds6_set_addr_iid(&ipaddr, &uip_lladdr);    /* 2. Set IID from MAC */
  uip_ds6_addr_add(&ipaddr, 0, ADDR_AUTOCONF);   /* 3. Add to interface  */

UDP Communication

both the sender and the receiver must register an UDP connection, a socket, with the following structure

int simple_udp_register(
    struct simple_udp_connection *c,  /* Connection state structure */
    uint16_t local_port,              /* Local UDP port to bind */
    uip_ipaddr_t *remote_addr,        /* Remote IP (NULL = any) */
    uint16_t remote_port,             /* Remote UDP port */
    simple_udp_callback receive_callback    /* Callback on packet receipt */
);

The remote IP address can be NULL, to indicate that packets from any IP address should be accepted

  • There are no broadcast addresses in IPv6. In IPv6, multicast addresses serve the same purpose as broadcasts
    • needs to configure also the multicast adress
  • Then, to send there are 3 functions: simple_upd_send, simple_udp_sendto, simple_udp_sendto_port


The udp_rx_callback function is the receive handler you provide to simple_udp_register(). Whenever a matching UDP datagram arrives, Contiki-NG invokes this callback with the following parameters:

static void
udp_rx_callback(
  struct simple_udp_connection *c,   // [1] Connection state (your udp_conn)
  const uip_ipaddr_t *sender_addr,   // [2] IPv6 address of the packet’s source
  uint16_t sender_port,              // [3] UDP port number of the source
  const uip_ipaddr_t *receiver_addr, // [4] IPv6 address we (the node) received it on
  uint16_t receiver_port,            // [5] UDP port number we bound to
  const uint8_t *data,               // [6] Pointer to the payload bytes
  uint16_t datalen                   // [7] Length of the payload in bytes
) { ... }

RPL Routing

The routing protocol (RPL in our case) enables multi-hop communication to allow nodes far from the network collection point to deliver their data.

  • Only hop-by-hop (layer 2 communication) is possible with link-local IPv6 addresses.

RPL builds and maintains a Destination-Oriented Directed Acyclic Graph (DODAG) topology that originates from an RPL root node, which is also the border router to the Internet.

  • Routing control messages are disseminated through broadcast beacons periodically.

The topology is built following a goal defined by an Objective Function.

  • e.g., minimize the estimated transmission count during transmission.

RPL supports different directions of traffic:

  • Upward routing: from any node to a root.
  • Downward routing: from the root to any node.
  • Any-to-any routing: where traffic flows between arbitrary pairs of nodes in the DODAG by routing upwards to their closest common ancestor (or the root in non-storing mode), and then downward to the destination node.

Downward routing is handled with two types of modes: non-storing and storing mode.

  • Storing mode:
    • Routing tables are stored on each node.
    • Can impose a significant memory footprint in large networks and be hard to maintain consistently.
    • No need for potentially large source routing headers in the IPv6 packets.
  • Non-storing mode:
    • IPv6 source routing is employed.
    • Nodes do not have to store routing tables.
    • Packets can get large if many hops are along the path (due to source routing headers).
    • Only downward packets get the extra headers; packets traveling upward are not affected.
    • The DODAG root node has to store the routing table of the whole network, so its memory usage will still be high in large networks.

To initialize the DAG root:

NETSTACK_ROUTING.root_start();

#include "sys/log.h"                       // Logging facilities

#define LOG_MODULE "App"                   // Log label for this module
#define LOG_LEVEL LOG_LEVEL_INFO           // Log verbosity level

#define UDP_CLIENT_PORT 8765               // Port where the client sends from
#define UDP_SERVER_PORT 5678               // Port where this server listens

static struct simple_udp_connection udp_conn; // Global structure for UDP connection

// Declare and register the UDP server process
PROCESS(udp_server_process, "UDP server");
AUTOSTART_PROCESSES(&udp_server_process);  // Automatically start the server process when node boots

// Callback function called when a UDP packet is received
static void udp_rx_callback(struct simple_udp_connection *c,
                            const uip_ipaddr_t *sender_addr,        // IP address of the sender
                            uint16_t sender_port,                   // UDP port of the sender
                            const uip_ipaddr_t *receiver_addr,      // IP address of receiver (this node)
                            uint16_t receiver_port,                 // UDP port on which data was received
                            const uint8_t *data,                    // Pointer to received data
                            uint16_t datalen)                       // Length of received data
{
  // Log the received message and the sender's address
  LOG_INFO("Received request %s ", data);
  LOG_INFO_6ADDR(sender_addr);
  LOG_INFO_("\n");
}

// Main thread of the UDP server process
PROCESS_THREAD(udp_server_process, ev, data)
{
  PROCESS_BEGIN();

  // Start this node as the DAG root (RPL root), which makes it the network's coordinator
  NETSTACK_ROUTING.root_start();

  // Register a UDP connection: 
  // - listen on UDP_SERVER_PORT
  // - accept data from any IP address (NULL)
  // - expect data to come from UDP_CLIENT_PORT
  // - use `udp_rx_callback` as handler when a datagram arrives
  simple_udp_register(&udp_conn, UDP_SERVER_PORT, NULL,
                      UDP_CLIENT_PORT, udp_rx_callback);

  PROCESS_END();
}
#include "contiki.h"                       // Core Contiki definitions
#include "net/routing/routing.h"          // For checking routing and getting root IP
#include "random.h"                        // For generating random delays
#include "net/netstack.h"                 // Access to the network stack
#include "net/ipv6/simple-udp.h"          // Simplified UDP API
#include "net/linkaddr.h"                 // For accessing the node link-layer address
#include "sys/log.h"                      // Logging utilities

#define LOG_MODULE "App"                  // Log label for this module
#define LOG_LEVEL LOG_LEVEL_INFO          // Log verbosity level

#define UDP_CLIENT_PORT 8765              // Local port to send from
#define UDP_SERVER_PORT 5678              // Destination server port

static struct simple_udp_connection udp_conn; // UDP connection handle

#define START_INTERVAL (5 * CLOCK_SECOND) // Timer interval (first message after 5 seconds)

PROCESS(udp_client_process, "UDP client");           // Declare the process
AUTOSTART_PROCESSES(&udp_client_process);            // Automatically start on boot

// Callback function called when a UDP response is received
static void udp_rx_callback(struct simple_udp_connection *c,
                            const uip_ipaddr_t *sender_addr,
                            uint16_t sender_port,
                            const uip_ipaddr_t *receiver_addr,
                            uint16_t receiver_port,
                            const uint8_t *data,
                            uint16_t datalen) {
  LOG_INFO("Received response %s", data);
  LOG_INFO_6ADDR(sender_addr);
  LOG_INFO_("\n");
}

PROCESS_THREAD(udp_client_process, ev, data) {
  static struct etimer periodic_timer;        // Timer to control sending interval
  static uip_ipaddr_t dest_ipaddr;            // IP address of the DAG root (server)
  static unsigned int message_number = 0;     // Counter for sent messages

  PROCESS_BEGIN();

  // Register UDP connection: this client sends from UDP_CLIENT_PORT,
  // expects responses from UDP_SERVER_PORT, and uses `udp_rx_callback` to handle replies
  simple_udp_register(&udp_conn, UDP_CLIENT_PORT, NULL, UDP_SERVER_PORT, udp_rx_callback);

  // Set initial timer
  etimer_set(&periodic_timer, START_INTERVAL);

  while(1) {
    // Wait until timer expires
    PROCESS_WAIT_EVENT_UNTIL(etimer_expired(&periodic_timer));

    // Check if the DAG root is reachable and get its IP address
    if(NETSTACK_ROUTING.node_is_reachable() && NETSTACK_ROUTING.get_root_ipaddr(&dest_ipaddr)) {
      // Log the destination and message number
      LOG_INFO("Sending request %u to ", message_number);
      LOG_INFO_6ADDR(&dest_ipaddr);
      LOG_INFO_("\n");

      // Create the message payload
      char buf[300];
      sprintf(buf, "Message %d from node %d", message_number, linkaddr_node_addr.u8[7]);
      message_number++;

      // Send the message via UDP
      simple_udp_sendto(&udp_conn, buf, strlen(buf) + 1, &dest_ipaddr);
    } else {
      LOG_INFO("Not reachable yet\n");  // Routing not yet ready
    }

    // Set the next timer with a randomized delay to reduce collisions
    etimer_set(&periodic_timer, (random_rand() % START_INTERVAL));
  }

  PROCESS_END();
}
