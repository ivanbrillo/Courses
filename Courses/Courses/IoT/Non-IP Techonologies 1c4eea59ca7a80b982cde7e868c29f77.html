ZigBee

There is no transport protocol layer

  • no need for multiplexing and demultiplexing since there is just one application
  • reliability will not be guaranteed by that layer
  • congestion control is not needed since low volume of data

The phisical layer and the mac layer are the 802.15.4 standard

  • ZigBee adresses only the upper layers

Device Types

  1. ZigBee Coordinator (ZC) → one is required for each network
    • it’s responsible for starting the network and managing the activities
  1. ZigBee Router (ZR) → intermedate nodes that forward the messages (multihop routing)
  1. ZigBee End Devices (ZED) → In the perifery of the network, are the final destination
    • doesn’t allow routing

Tologies

Three topologies defined:

  1. Star
  1. Mesh → graph topology
    • Non-beacon enabled mode is used
    • The coordinator and the routers must always be on → not energy constrained or energy harvesting system
    • End devices can wake up at any time they need to communicate since the routers and the coordinator are always on
  1. Cluster Tree → tree topology, intermediate one
    • generally not supported
    • root is the coordinator, other internal nodes are routers, leafs are end devices

Routing Protocol - AODV

AODV: Ad-hoc On-demand Distance Vector

  • on demand since is lazy and not proactive

Consider the Mesh Topology (since star is obv and the other is not supported)

  • Non-Beacon Enabled mode

We cannot use traditional routing protocols since they are all conceived with routers all active and long range

  • but energy could be a problem for routers in these networks

Don’t calculate path in advance in order to save energy

  • reactive approach (lazy) and not proactive like in traditional internet
    • only when necessary (a node want to send the msg to a specific destination)
  • The latency will increase, but less bandwidth necessary and also less energy consumed
    • Unlike proactive protocols that continuously update all routes, reactive protocols only update routes that are actively in use (in case of crash)

Based on sequence number in order to:

  1. prevent loops
  1. select the most recent path

Routing Table

The routing table provide the next hop towards a given destination (useful for end devices)

  • It’s mantained in every router
  • Every destination has an entry in the table
  • there is a lifetime associated with each entry
    • Refreshed the timer every time the path is used
    • when the lifetime expiration the entry is purged → network topology changes

When in discovery better not to use the information (routes are not yet fully established or confirmed, may not be the optimal)

Forwarding Algorithm

Different from rounting, since forwarding is send the packed along the path, while routing is finding the path

  1. A packet is received
  1. Is this device the end destination? → If yes pass to higher layer to process
  1. Otherwise is the packet adressed to a device connected to this router? → If yes route to the child
  1. Otherwise is there a routing table entry for the destination? → If yes route to the text hop
  1. Otherwise are there resources (energy) to start a route discovery? → If yes initiate route discovery
  1. Otherwise route along the tree (parent node)

Route Discovery

Made in Non-Beacon mode (routers are always active)

Based on two control packets:

  1. Route request (RREQ)
  1. Route reply (RREP)

Source node S:

  1. Broadcast a RREQ
  1. waits for the corresponding RREP

Intermediate Node X:

  1. RREQ from Y →
    1. creates an entry in RT with the inverse path: Y next hop, S destination
      • used to forward the RREP back to S
    1. re-broadcast the RREQ
  1. RREP from Y →
    1. creates the forward path in the RT: Y is the next hop to D
    1. forwards RREP to S using the reverse path

  1. not considered end devices, but just router (not important in the path discovery) and links bidirectional
  1. Imagine S start with the routing table with only {F:C}\{F: C\}{F:C}﻿
  1. Start by broadcasting the RREQ with the destination G and it’s origin S
  1. B and C implicitly understand that is possible to trasmit to S
  1. B and C broadcast the received RREQ to the neighbours D and E
  1. D realizes that they can reach the originator S by trasmitting to B → new entry on the routing table (same thing with E)
  1. D and E retrasmit to neighbours → they will re-receive the RREQ with the same ID and will be managed - next slides
  1. Update the routing tables of H and F
  1. G send back the RREP → the path to S is already learnt by the previous nodes
  1. S update the routing table {F:C,G:B}\{F: C, G:B\}{F:C,G:B}﻿
  1. Subsequent RREP with longer paths will be discarded, otherwise update RT

Route Discovery Table (RDT)

In addition to the Routing Table there is another table, the Route Discovery Table (RDT) which is maintained by routers and the coordinator to implement route discovery.

Used for:

  • avoiding loops
  • choosing the most efficient path
  • removing the expired path

RREQ Processing

Each RREQ message carries a RREQ ID which the originator increments every time it sends a new RREQ message

  • In this way the RREQ ID and source address can be used as a unique reference for a route discovery process.

When a RREQ arrives at an intermediate node (router):

  • fwd cost is sent with the RREQ and increased at each hop
  • Update the RDT and RT entry each time → discovery because may exist some better paths

when send RREP also RT active?

RREP Processing

Note that intermediate nodes never change the RT entry status to Active as a result of receiving a RREP message

  • They will only change the entry status upon reception (and routing) of a data message for the given destination

Route Maintainance

Suppose node X detects that its link to X1 is broken (e.g., due to signal loss, node X1 moving out of range, or power failure).

  • Since X was using this link to forward packets, it must notify the network about the broken path

URR (Unsolicited Route Reply) is a message sent to notify upstream nodes (nodes that rely on X for routing → X look at his own table the destinations that could reach) that the path involving X → X1 is no longer valid

  • This message propagates backward toward the source node to inform it that it must find a new route
  • When a node receives a URR, it invalidates its own routing table entry for that destination
    • Then forward the URR
  • The source node S upon receiving URR, S starts a route discovery phase to find a new path to the destination

  1. X marks affected entries as invalid in its routing table
  1. X sends URR (Unsolicited Route Reply) messages for each affected destination (D1 and D3)
  1. URR propagates backward to nodes that were using X to reach these destinations
  1. Each node receiving URR checks its own routing table and forwards the URR if it was using the broken path
