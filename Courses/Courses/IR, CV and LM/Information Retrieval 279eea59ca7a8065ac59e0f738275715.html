Indexes

We can measures the performance of an index data structure:

  • indexing time: time needed to build the index
  • indexing space: space used during the generation of the index
  • index storage: space required to store the index, once it has been generated
  • query latency: time interval between the arrival of the query in the IR system and the generation of the answer
  • query throughput: number of queries answered per second

Inverted Index is a data structure providing mapping between terms and their location in documents

  • dictionary: list of all dinstinct index terms
  • Each document is given a unique number called docid
  • posting list associated to a term: list containing documents (or locations) where the term appears
    • typically document ordered

Case 1: Posting List = [docid]

  • Allows to search for any (union) or all (intersection) query terms
  • No ranking possible
  • No proximity match or phrase match

Case 2: Posting List = [docid : term_freq]

  • Allows ranking by relevance
  • No proximity match or phrase match

Case 3: Posting List = [docid : positions]

  • Allows relevance ranking, phrase match and proximity match (find small within 5 words of marsupial)

Case 4: Posting List = [docid : impact score]

  • widely used in production

Auxilliary data structures of inverted index:

  1. Lexicon (or Vocabulary): contains term stats across whole connection
    • document frequency df [number of docs where it appears at least once]
    • cf (collection frequency) - total number of occurrences of the term across the whole collection
    • lookup table from the term to byte offset of the inverted file (inverted index)
  1. Document index contains information on the single documents (e.g. URL, title, doc len, importance scores, …)
  1. Collection Statistics: stored in a separate file, contains total number of docs, total numbers of terms, total number of postings, …
  1. Direct Index: index mapping documents to termids and their frequencies

What is a term for indexing?

  1. Any string between two separating symbols → full-text indexing
    • Problems for things like “New York City”
  1. By important keywords → keyword indexing
    • only terms from a given list
  1. Phrase indexing
    1. common phrases (eg good morning)
    1. bigram
  1. Term pair indexing: eg. all the documents that contain both “cat” and “dog” → not sequentially
    • much larger index with more inverted lists, but each one much shorter than single-term lists

How to store these structures?

  • At end of indexing, each structure should be a file(s) on disk
  • Lexicon and document index are smaller than inverted index
  • Note: lexicon stores term frequencies, document index stores ∣D∣|D|∣D∣﻿

Lexicon Layout

  • Contains one element for each distinct term (term is the key)
    • Dictionary, hash table, succinct data structure or disk based data structure
    • Stores start of corresponding posting list (file offset for disk-based index or a pointer)
    • Also stores length of list, maybe other items → If you know offset and length_bytes, you can seek(offset), read(length_bytes) and stop without looking for a sentinel
      • useful in particular for compression

Document Index Layout

  • Contains one element for each indexed document
  • Keeps the mapping between documents (URL/docno [external identifier]) and docids
    • Maybe store document size and pagerank
    • Simplest approach: records ordered by docid → because they are typically dense, thus access in O(1)O(1)O(1)﻿ when the elements have constant size
    • More space-efficient:
      • Since URL has variable size, move to another file and keep a pointer or offset → this allows lookup of docid by URL
      • Store URLs in alphabetic order, maybe compressed

Inverted Index Layout

  • The inverted index is usually stored on disk, and in memory
  • Usually multiple inverted indexes, with a constant number of documents per index
  • In compressed form, even if in memory (never ever fully decompressed)
  • De-facto posting format is (docid, frequency)
  • Do not store docids and frequencies in interleaved form
