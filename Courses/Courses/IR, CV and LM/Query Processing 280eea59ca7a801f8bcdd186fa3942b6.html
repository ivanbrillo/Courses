Query Processing

  1. Boolean retrival → suitable for small/medium collections
    • returns all documents matching the query
  1. Ranked retrival → suitable for large collections (web-scale)
    • returns only the top K matching documents → define a similarity function: sq(d)=∑t∈qst(q,d)s_q(d) = \sum _{t \in q} s_t(q, d)sq​(d)=∑t∈q​st​(q,d)﻿
      • s:Q×D→Rs: Q \times D \rarr \mathbb{R}s:Q×D→R﻿, then order the terms
      • sum of score dependent on each term
      • for each term this information is inside the posting list
      • If it doesn’t appear on a document it’s score is zero
      • depends on dd d﻿ to count the words and on qqq﻿ to normalize for example
    • Useful for not returning 1000s or results, and since most users are incapable of writing boolean queries (logic operators)

We consider the document in a conjuctive (AND, all terms) or disjunctive (OR, at least one) way

  • makes no sense to use disjuctive in boolean retrieval

TAAT - Term at a Time

In ranked disjunctive retrieval, the posting lists can be traversed one query term at a time

  • Use a score function called TF → term frequency

    sTF(t,d)=tfd,ts_{TF}(t, d) = tf_{d, t}sTF​(t,d)=tfd,t​﻿

  • Scan for each term the structure sequentially, put everything inside an accumulator table
    • Posting list are sorted by increasing docid, while accumulator table is sorted by score
    • Then for the next term, start summing the scores for the docid

  1. Cache-friendly → because we exploit spatial locality, since posting lists are stored sequentially
  1. Accumulator table is huge → bounded by the number of docs
  1. Sorting is not a problem since it’s not necessary

DAAT - Document at a Time

In ranked disjunctive retrieval, the posting lists can be traversed all query terms in parallel, to fully process a document at a time

  • initialize an iterator on all posting lists exploiting the fact that they are sorted
  • Since I can compute directly the score, I do not need an hash map, but I can keep it directly inside the priority queue

  1. Smaller memory footprint than TAAT, just a priority queue
  1. Support boolean and phreasal queries
    • natural to force boolean constrains like term2 not present, or something like: term2 and 3 or 4
    • checking the position information I could also see if term2 and term5 are next to each other
  1. With no modificiation, it can run on distributed inverted index
  1. Less cache-friendly than TAAT

Distributed Query Processing

  1. All queries sent to a manager machine, manager then sends messages to many index servers
  1. Every index server (stores a portion of index) must process the query locally
  1. The results are collected and aggregated by a manager machine to produce the final top K results

The two main approaces are

  1. Document distribution (distributed local indexing) → most used
    • Each index server acts as a search engine for a small fraction of the total collection
    • Each machine returns the top k local results and then are merged and keep the best k
    • Collection statistics should be shared for effective ranking (e.g. tfidf)
    • slowest one dominates the time required to serve a single query
  1. Term Distribution (distributed global indexing)
    • Each inverted list in the whole single index is assigned to one index server
    • In most cases the data to process a query is not stored on a single machine
    • No need to use all servers (just the ones that have the query terms)
    • now we need to wait just few servers to serve the query, not all
    • Load balancing depends on the distribution of query terms and their co-occurrence
    • One of the index servers is chosen to process the query (master)
      • usually the one holding the longest inverted list
      • other index servers send information to that server

Caching: about 50% of the queries each day are unique, but some are very popular

  • About 15% of the queries per day have never occurred before

Should cache the popular query results and the commont posting lists (to store it in the query server)

  • Cache must be refreshed to prevent stale data

Compression

Compression for inverted index → in order to make it fit in RAM and not in disk

  • tradeoff to compress as much as possible but not wasting too much time in decompressing it

We can compress (typically both):

  1. The lexicon (vocabolary) → because it needs to be accessed for every single term for every single query
    • Smaller it is, more posting lists can be kept in memory
  1. The posting lists (inverted index)
    • decrease the time to read them from disk
