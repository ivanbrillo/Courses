Web Crawiling

Web crawling is the process of locating, fetching, storing, and maintaining the pages available in the Web.

  • Computer programs that perform this task are referred to as: crawlers, spiders, harvesters
  • Web crawler repositories cache the online content in the Web, provide quick access to the physical copies of pages in the Web, help to speed up the indexing process

Web crawling:

  1. Initialize an URL download queue (URL frontier) with some seed URLs
    • Good seeds will like to many pages (e.g. home pages)
  1. Repeat:
    1. Fetch the content of a URL from the download queue
    1. Store the fetched content in a repository
    1. Extract the hyperlinks of that document
    1. Add the links to the download queue

Problems:

  • To fetch 1bn of pages in one month we need to fetch 400 pages per second
    • Actually many more since many will be duplicates already visited
  • Needs to be:
    1. distributed
    1. avoid duplicates or near duplicates
    1. need to understand when to recrawl the site

Incremental Web-Crawling

Devides the web in 3 sets (pages will move between those in time):

  • downloaded
  • discovered → frontier
  • undiscovered

Web crawler components:

  • URL Frontier can be sorted to give priority to some pages
  • Seen URLs: a set data structure, permitting the crawler to know if it
    has crawled a URL before or not
  • Fetcher: downloads an unseen URL & store it in the data repository
  • Parser: extracts outgoing links from the page
  • URL Filtering: eliminate URLs that appear to be images, or that are
    disallowed by the robots.txt files
  • Content-seen filter: eliminate duplicate pages

Distributed Search

To satisfy high query loads, the retrieval process needs to be spread over many CPUs and hard disks

  1. Vertical scaling
  1. Horizontal scaling → used also to parallelize the indexing process itself
    1. Spread the index in shards running on many machines
    1. Replicate the shard multiple times (allow the query to be processed in parallel and for fault tolerance)

  1. Term Partitioning
    • different nodes (server) are associated with different subset of the vocabulary (e.g. A to D, …)
    • During query processing, different queries touch different query servers
    • The query load is automatically spreaded over different query servers (the ones with the query terms)
  1. Document Partitioning
    • NNN﻿ Documents are allocated to PPP﻿ different nodes
    • During query processing, each server executes the query on about N/PN/PN/P﻿ documents
    • The results from each of the servers are combined into a final result list
    • Load is on EACH query server

I could perform different document partitioning:

  1. Random → good for efficiency on large collections: all queries touch all partitions
  1. By semantic/topic, e.g., if collection is already organised into semantically meaningful sub-collections
    • A query targets particular sub-collections
    • News, tweets, webpages, images

    We want each collection to be “well separated”, such that query maps to a distinct collection containing the largest number of relevant documents

    • E.g. by language: permits geographically distributed data centres
    • E.g. by examining a query log, and clustering documents by the queries that touched them

    How do we tell which partitions can answer a query?

    • Resource selection techniques (CORI, ReDDE): statistical predictors if a sub-collection can answer a query
    • Learn if a sub-collection is good for a query: e.g. present users with news results, see if they click

A distributed retrieval setting is coordinated by the broker

  • It passes the query to the nodes and collectes the top-k results for the user
  • Typically the query servers are replicated to increase throughput and fault tolerance

Learning to Rank

Traditional ranking functions in IR use a very small number of features

  • Term frequency, inverse document frequency, document length

Modern (web) systems use a great number of features

  • NYT in 2008 quoted said that Google was using over 200 such features (“signals”) → so it’s sure to be over 500 today

A generative model assumes that documents were generated from some underlying model P(d∣relevance score)P(d | \text{relevance score})P(d∣relevance score)﻿ and uses training data to estimate the parameters of the model

  • Probability of belonging to a class (i.e. the relevant documents for a query) is then estimated using Bayes’ Rule, the document model and a prior P(C)P(C)P(C)﻿
  • Most of the retrieval models presented thus far in this course (e.g. TFIDF, BM25, LM) fall into the category of generative models
  • Generative models perform well with low numbers of training examples [but typically irrealistic assuptions, like word independence]

A discriminative model estimates the probability of belonging to a class directly from the observed features of the document based on the training data

  • They models directly the posterior P(C∣d)P(C | d)P(C∣d)﻿
  • Discriminative models typically rely on “machine learning”
  • Discriminative models usually perform better given enough training data
    • They require large training datasets, possibly instantiated from click-through data
    • Click-through data has facilitated the deployment of learning approaches

Ranking is a regression (ordinal regressions), not a classification

  • The classes are ordered, while in classification are not

Typically, commercial search engines use hundreds of features:

  1. Query-document features
    • Weighting models, e.g. BM25, LM
    • Field-based weighting models, e.g. BM25F
    • Deep-learned semantic matching (more on that later)
  1. Query-independent features
    • Number of outgoing links in a web page
    • Number of ingoing links in a web page
    • URL length, title length, spam score
  1. Query-only features
    • Number of terms
    • Number of stopwords
    • Number of entities

Features in LTR models (learning to rank) do not include the presence of a specific word in a document (but directly the BM25)

LTR Steps:

  1. Sample identification (10s documents)
    1. Use BM25 to rank the documents wrt a training query
    1. Hope that the sample contains enough relevant docs
  1. Feature computation
    1. query-docs and query-only features
  1. Learn the ranking model with the traing data (in inference i will use the learned model to rank)

Problems:

  1. We need lots of queries with assessed documents to learn an effective and robust model
  1. We can’t measure the “success” of a learning-to-rank technique on the queries it has been trained upon
    • We need to separate the queries in our test collection into disjoint sets:
      1. One training set, to train the model
      1. One validation set, to tune the learning hyper-parameters
      1. One test set, to test how effective the model is for unseen queries

A loss function is used to estimate how good a particular model is, based on training data

  • The learning algorithms will try many different models to find the best one, i.e., the model minimising the loss (on the training data)
  • There are three types of learning procedures (and associated loss families) appropriate for ranking tasks
    1. Point-wise approaches → closest to classification/regression
      • Classification: how many documents did the learner correctly predict as relevant/non-relevant?
      • Regression: how different is the predicted score from the correct relevance label for each document?

      Limitations:

      1. They consider each document independently, instead of trying to get the relevant documents ranked above the non-relevant ones (e.g. r(di)=3r(d_i) = 3r(di​)=3﻿ instead of ensuring r(di)<r(dj)r(d_i) < r(d_j)r(di​)<r(dj​)﻿) → the position in the rank is not accounted in the loss
      1. They ignore the fact that some documents are associated with the same query and some are not → this means the model doesn't explicitly focus on within-query comparisons
      1. If the number of documents varies largely for different queries, the overall loss function will be dominated by those queries with a large number of documents → biased

    1. Pair-wise approaches → Try to minimise a loss function based on the ranking error between pairs of documents
      • Consider a query qqq﻿ and two documents, did_idi​﻿ and djd_jdj​﻿, with did_i di​﻿ more relevant than djd_jdj​﻿
      • Try to learn a function f(q,d)f(q, d)f(q,d)﻿ such that f(q,di)>f(q,dj)f(q, d_i) > f(q, d_j)f(q,di​)>f(q,dj​)﻿

      Limitations:

      • Pairwise losses are typically unaware of where in the ranking the documents appear. They treat all pairs equally (or mostly equally) rather than weighting errors that occur at the top of the list more heavily.
      • The number of document pairs per query is quadratic in the number of documents for that query
    1. List-wise approaches
      • Consider the entire ranking of documents for a query
      • Encapsulates a standard IR evaluation measure within the loss function
      • Not all the metric are appropriate
        • P@3P@3P@3﻿ is not good, since in the first 3 doesn’t consider the order, and doesn’t consider what is retrieved after the third document
        • NDCG@1000NDCG@1000NDCG@1000﻿ handles both relevance levels and looks down the retrieved documents

Linear Models → linear combinitation of features values

  • f(q,d)f(q, d)f(q,d)﻿: A feature function that extracts some property from the query-document pair
  • wfw_fwf​﻿: The weight/importance of feature f

Problems:

  • They assume that the same features are needed by all queries
  • the underlying model is linear
  • independence of wjw_jwj​﻿ among different queries and documents
  • To learn wjw_jwj​﻿ we cannot use SGD since the problem is not continous and thus not differentiable
    • Loss doesn’t respond to changes in the scores of document, but only when a swap between the ordering of two documents takes place
    • Advanced algorithms needed for the porpouse

Tree Models

  • a regression tree is composed by series of decisions, leading to a partial score output
  • The output of a learner is a “forest” of many regression trees, used to compute the final score of a document with respect to a query
  • Their ability to “customise branches” makes them more effective than linear models
  • Regression trees are point-wise in nature, but several major search engines have created adapted regression techniques that are list-wise (e.g BING)
