Hardware Assisted Virtualization

Hardware virtualization techniques result in running the guest OS completely into user space

In fact, every time the guest OS switches to kernel space, we have a context switch to run the VMM, which mimics the execution of a privileged instruction or other operations (e.g. I/O)

  • Although guest OS kernel operations are limited in time, they represent a significant performance penalty, due to the noticeable overhead in performing hardware emulation and instruction emulation

AMD and Intel add new features that are explicitly designed to support efficient implementation of VMM-Hypervisor software

  • Intel and AMD extensions are equivalent; thus, we focus on the Intel extension called VMX (Virtual Machine eXtension)

VMX technology introduces two new operating modes in Intel CPUs: the root (for VMM) and non-root (for VM) modes
The result is four possible combinations (in order of privilege):

  1. root/system → kernel of Hypervisor
  1. root/user → code of Hypervisor but not core one or user applications
  1. non-root/system → guest OS
  1. non-root/user → a VM application

The main purpose of these new modes is to put hardware-controlled limitations to the actions performed by the guest OS

  • Whenever the guest OS tries to execute an instruction that would either violate the isolation of a VM or require software emulation, the hardware can trap and switch back to VMM execution

Two new assembly instructions are introduced, the VMLAUNCH and VMRESUME, which both enable to launch the VM

  • Those instructions are only allowed in root/system mode
  • They reduce overhead, since only one instruction is needed for the context switch (save or load all the data of VM in a data structure)

  • The VM returns to the root mode and switch back to the VMM execution for a number of reasons, named VM exits
  • Tunable list of operations for VM to run them autonomously → reduce overhead

The non-root mode, via additional hardware support, allows the VM running in non-root mode to (we will see the details later):

  1. Execute some privileged instructions
  1. Handle directly (some) interrupts

This without requiring VMM intervention for their emulation

Interrupt Management

To re-route interrupts an additional table is added, the Interrupt Remapping Table (IRT)

  • The IRT allows to re-route every hardware interrupt directly by the VMM in a dynamic manner
  • It has an entry for each possible interrupt request
  • for IO devices (used in IOMMU)

Trap Management

Each entry maps the requests to the interrupt vector of a VM or to the interrupt vector of the VMM

  • Every time an interrupt is triggered, the IRT decides which Interrupt Vector handles the interrupt

An example is the need to emulate via software the execution of two instructions:

  1. INT (interrupt) is used when a program needs to request system services - moving from user mode to system mode
  1. IRET (interrupt return) is used to return back to user mode from system mode

Without hardware support, their execution was emulated via software by VMM, which was responsible for taking care of modifying the VM status in order to mimic the execution of the instructions

  • With root and non-root modes the execution of INT and IRET can be performed without the need to execute VMM code: whenever the INT is invoked the operating mode is switched from non-root/user to non root/system → no emulation
    • with IRET is the opposite

The VMM only needs to step in if:

  • The instruction causes a VM Exit - like executing an instruction that is not allowed in non-root mode (e.g., accessing CR3 or I/O ports directly)
  • VMM places a trap in the VMCS

VMCS

Intel VMX introduces a new Structure (VMCS) Virtual Machine Control Structure, which is a control structure that contains all the information associated with the state of a VM (unique for each running VM)

  • The extension includes a set of instructions to manipulate such data structure that are used when the context switches to execute the VMM or the VM is restored → carried out in hardware

VMCS data structure has several fields that can be grouped as follows:

  1. Guest state: stores the state of the (virtual) processor associated with the VM. The state is loaded from the structure to the processor during VM launch, while during a VM exit the state is stored back
    • Contains the instruction pointer, that points to the first instruction to be executed after VM launch
  1. Host state: store the state of the physical processor before the VM launch. It can contain the state of the VMM, running before VM launch. The state is restored during a VM exit, while it is saved at VM launch
    • The host state contains the value to be loaded into the instruction pointer at VM exit, to recover the execution of the VMM
  1. VM execution control: this field specifies what kind of operations and the instructions that are allowed and not allowed during non-root mode. Unallowed actions cause a VM exit (bitmap)
    • Flags to determine the behaviour of an interrupt or a I/O management, exploited in particular for peripheral passthrough
      • A flag determines what should happen when the CPU receives an external interrupt, while running in non-root mode. Through this flag VMM can specify if the VM can handle interruptions directly or a VM exit must occur
    • A flag determines whether some critical instructions should cause a VM exit or they can be executed by the VM
    • Another set of flags specifies if I/O operations are allowed inside the VM or a VM exit is required
  1. VM enter control: it contains several flags and fields that determine some optional behaviors during the transition from the root to non-root (bitmap) → hardware automatic operations
    • Fields that can be used by the VMM to mimic a fake external interrupt or to inject exceptions and fault
    • The VMM writes the vector of the desired interrupt into the VM enter control, during VM enter, the processor will perform all the actions to mimic the interrupt reception, specifically:
      1. it saves the state on the guest stack
      1. it looks up the guest interrupt descriptor table to determine the address of the interrupt
        handler
      1. it modifies the registries of the CPU to execute the handler
    • Through this mechanism, fake interrupt can be generated into a VM by the VMM
  1. VM exit control: likewise, but for the non-root to root transition
  1. VM exit reason: it contains information related to the reason that caused the latest VM exit event

RAM Management

Both AMD and Intel have added some extensions to their hardware support to simplify the task of virtualizing guest virtual memory → I have an overhead every time I need to trap the changes

  • Specifically, they introduced the extended page table, that is available on the host but not on the hardware emulated for the VM
  • The hardware implementing the host MMU is extended to have two PTBR pointers, one to the page table of the guest VM, implementing the G mapping, another one to the page table created by the VMM to implement the H mapping
  • The extended hardware takes care of applying the composition of G mapping and H mapping, which are applied sequentially in hardware by the MMU
    • No longer need the multi-level trick of brute force

Through this extension, there is no longer any need for VM exits, every time the guest VM modifies the page table

  • This extension, however, increases the cost for address translation, which is more expensive, as more memory accesses must be performed by the hardware → two entire traslation instead of a little longer one with shadow pages (one more level)
  • In order to reduce this overhead, the latest MMUs are usually equipped with a page table cache to reduce those accesses

Hardware Passthrough

I/O emulation poses the biggest performance challenge in virtual machines

  • VMM has to participate in every interaction between the VM and the I/O peripherals (often emulated), thus resulting in several VM exits

In order to overcome this issue, a solution is to give a VM direct and exclusive access to a peripheral

  • This approach is called passthrough and maps the device directly to the guest VM without performing any translation
  • This eliminates completely the need for VM exits, however, the hardware is not virtualized, and it must be dedicated to one VM and not shared
  • No abstraction layers

In order to implement this approach explicit hardware support is required

In order to implement a passed through device to a guest OS running into a VM, we need two main functionalities:

  1. Direct mapping of the I/O (physical) memory space in the virtual physical memory of the VM, so the guest OS can write directly on the registries of the peripheral
  1. Direct assignment of the interrupts linked with the peripheral, so the VM can handle the interrupts coming from the passed-through device, while the VMM handles all the others

Direct Mapping

For read/write to/from the registers of the passed-through device, we want the VM to be allowed to perform I/O read/write without VMM intervention

  • Intel VMX architecture includes in the VMCS an I/O bitmap, with one bit for each possible I/O address to specifically support hardware passthrough (check adresses that can be accessed directly from VM)
  • When a device passthrough is set for a VM, the I/O bitmap is modified in order to set all the bits corresponding to the addresses of the I/O space of the device, to grant direct access
  • In non-root mode, the CPU first checks the bitmap when a read/write is performed in the I/O space: if the bit is set the instruction is completed, otherwise a VM exit is triggered to give back control to the VMM (e.g. to emulate hardware operations)

Interrupts

Direct Assignment

Intel VMX extensions allow two options for the management of interrupts:

  1. the interrupt causes a VM exit, so the interrupt is managed by VMM
  1. the interrupt is managed directly by the VM without a VM exit

For passed-through devices, the second option is adopted: the interrupt is handled directly by the guest VM that receives the interrupt and executes the handler

  • In this case, the hardware is capable of directly looking at the Interruption Vector Table (IVT) of the guest OS and executing the corresponding handler of the guest OS
  • That is implemented via the Interrupt Remapping Table
  • The VM, however, might receive an interrupt while not running, to this aim the system needs to handle the interrupts coming from the passed-through device also when the VM is not running

VM needs to access directly GPU, since they cannot be virtualized in an efficient manner → Efficient ML training

Ready when the VM CPU is stopped because the host CPU is currently being used by the VMM or some other VM

  • When the guest software inside the VM executes the hlt instruction, the VMM typically intercepts the instruction and puts the VM into the halted state

  • A VM might resume from the halted state only if it receives an interrupt that is received to the VM CPU (power on from the VMM or interrupt that is received from the passthrough device)
    • Some devices has this function eg remote turn on from the internet adapter

When a passed-through device is involved, the interrupts should be managed according to the VM state. Specifically, we have the following three possible cases:

  1. VM running: the interrupt should be handled directly by the processor, jumping to the guest OS interrupt handler, without VMM intervention
  1. VM ready: since the host CPU is currently running something else, we want to store the interrupt request somewhere so that the VM CPU can handle it at the later time when the VM is scheduled for execution
  1. VM halted: the interrupt needs to be stored and the VM state needs to be changed to ready → mimic the behaviour of a physical system that is turned off

The posted interrupt mechanism, available in recent CPUs, allows the implementation of this mechanism

The posted interrupts mechanism allows to store interrupts signals (post) for later notification to the VM, without VMM intervention

  • The mechanism exploits an additional data structure for each VM: the Posted Interrupt Descriptor (PID)

Each entry in the IRT maps to an Interrupt Vector (if the interrupt must be handled by VMM) or a PID, which points to the actual interrupt vector if the VM is active

  • It is the VMM that modify this table
  • Automatically executed the interruput from VM, without a context switch

The PID contains information on the status of the VM and stores the information on the interrupt notifications for asynchronous notification. Specifically, it has the following fields:

  1. A Posted Interrupt Request (PIR) structure, in which interrupts are posted → but cannot be served immediatly
  1. A Suppress Notification (SN) flag that determines whether the controller after posting the interrupt in the PIR must also notify the CPU (SN=0) or not (SN=1) → eg. when VM is in ready state)
  1. A Notification Vector (NV) that points to the actual interruption vector of the VM
    • When the VM is in halted state it points to something else (wakeup notification vector)

The following operations are performed after receiving an interrupt:

  1. It sets the proper bit in the PIR
  1. If SN is 1 (e.g. because the VM is in ready state), it does nothing else:
    1. If the VM is running it interrupts the processor by using the vector NV
    1. If the VM is halted it triggers the awakening of the VM

  • When the VM goes into running state, VMM sets SN = 0 and NV to a vector named Active Notification Vector that points to the IDT of the VM
    • It must check also the PIR if some bits are set → unhandled interrupts
  • When the VM goes into ready state, VMM sets SN = 1
  • When the VM goes into halted state, VMM sets SN = 0 and NV to a special vector named Wakeup Notification Vector that triggers VM awakening

DMA devices

DMA devices are I/O devices that reads data directly from RAM

  • The CPU instructs the device by writing/reading on a small subset of registers, then it directly fetch the data from RAM
  • DMA devices access directly the physical memory

In order to translate virtual addresses into physical addresses, DMA devices exploits a specific MMU circuit for I/O (hardware peripheral)

  • This IOMMU is responsible for translating virtual addresses into physical addresses for the I/O device to read/write from/to RAM
  • The IOMMU is a general device that it was introduced into multiprogrammed systems that adopted virtual memory

IOMMUs are also capable of triggering page faults interrupts, if they found pages that are not stored in ram

  1. CPU Writes to DMA Controller Registers
    • Source address (e.g., the location of data in RAM or an I/O device)
    • Destination address (where the data should be transferred)
    • Transfer size (how much data to move)
    • Control information (e.g., transfer mode)
  1. DMA Controller Takes Over the Transfer
    • Once the CPU sets these registers, it sends a request to the DMA controller and then continues executing other tasks.
    • The DMA controller reads these register values and begins transferring data directly between RAM and the I/O device.
  1. CPU Gets an Interrupt When Done
    • After completing the transfer, the DMA controller signals an interrupt to the CPU, letting it know the transfer is finished

Nested Virtualization

Nested virtualization describes a system in which the hypervisor runs inside a VM, which in turn is running inside a host hypervisor

  • Nested virtualization is useful mainly for testing, although today is used also in solutions for production (it reduces the effort for upgrading the infrastructure)
  • It allows cloud consumers to setup their own IaaS infrastructure on top of a set of VMs running on a IaaS infrastructure

Multi-level nested virtualization requires specific hardware support

  • Intel and AMD only supports a single virtualization level
  • Guest Hypervisor doesn’t have hardware support → slower
  • Multiple virtualization levels can be multiplexed into a single virtualization level, when the two hypervisor are the same
    • Coordination between the two hypervisor → the inner one ask the second to do the action
  • Guest hypervisor access to hardware extensions for virtualization are emulated by the Host hypervisor
