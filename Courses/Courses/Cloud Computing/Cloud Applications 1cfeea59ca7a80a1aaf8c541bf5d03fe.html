Cloud Applications

Cloud applications are distributed systems, made of different components interacting each other to eventually offer an application to users

  • The implementation and integration of different software components for the cloud environment is a complex task that can result to be time consuming and expensive
  • want short time to market → rigourous methodologies

Requirements

In order to have mantainable code and short time to market:

  1. Interoperability → easy interaction with other components
    • expose a standard interface that can be easly invoked by other
  1. Scalability → horizontal scalability, the application should be designed to scale dynamically and effortlessly
  1. Composability → should be designed in order to allow its usage with different components without changes (failure of components or creation/destruction of VMs)

SOA - Service Oriented Architecture

Most suited style for software design for cloud applications

  • Software components in SOA are referred as services, which is a self contained component that implements specific functionalities
  • In SOA applications are built as a collection of services (or microservices) from existing software components
    • highly modular
    • different programming language

Services communicates via messages

  • Each msg has a specific schema
    • Does not only define the service (what it does and what information provides) but it also describes the message exchange patterns to interact with the service to invoke a certain functionality or to get certain data
  • Internal implementation is hidden


In SOA, components communicate through message passing, typically over standardized, agnostic protocols (e.g., HTTP with XML or JSON).

  • This contrasts with technologies like Java RMI - which require both caller and callee to share the same programming-language stubs, libraries, and runtime environment - thereby creating a tight coupling and technology dependency.

Roles

Two roles: consumer and provider

A consumer is a component that requires data to a provider and consume the data returned

  • a service could be one or both

In general service consumer and provider doesn’t interact directly because they do not know each other

  • A third party is intrduced and is called broker
  • once the identity and description is retrived then the two services will communicate directly

  • The broker is responsible for creating a service catalog (or registry) available services are enlisted → identity (IP) and interface

Advantages

  1. Loosly coupling approach → makes the system flexible to changes (since internal implementation is hidden) and expandable
  1. Composability → application created by the composition of existing services (reusability)
  1. Stateless

SOA services that are stateless and loosely coupled are perfect to adapt to the scalability of the cloud infrastructure

  • As a new instance of a service is created (e.g. because the number of requests increased and novel VMs are created with a specific service) they are registered to the broker and made available to consumer
  • Viceversa when destroyed are removed in a trasparent manner

Web Services (WS)

The Web has become a medium for connecting remote clients with applications

  • The term Web Service (WS) is often referred to a self-contained, self-describing modular application designed to be used and accessible by other software applications across the web
  • A web service is a software system designed to provide interoperable machine-to-machine interaction over a network

3 pillars of Web

  1. URI
  1. Communication Protocol (HTTP)
  1. Data Encoding (HTML) → it is not suited to encode application data
    • XML is introduced for this porpouse (hyerarchical structure)
    • Grammar specifications, i.e. what kind of information can be written on document, are also available but not mandatory
    • Extensible, since the set of tags is not predefined

XML is composed of (hyerarchical structure):

  1. elements → begin with a start tag and ends at the end tag
  1. document usually begins with a root declaration, describing the metadata of the doument itself
  1. Attributes are name-value pair that can be specified within a start-tag

XML document may have an associated schema (grammar of the document)

  • In the validation it is marked as valid/non valid

SOAP

2 Protocols for the interaction of the three components.

A WS has an interface described in a machine executable format, the Web Services Description Language (WSDL)

  • WSDL is used to interact with the broker, a module that provides a global registry for advertising and discovering web services.

  • Via WSDL each service provider register itself to the broker, while the service consumer uses WSDL to look up for a specific service

Service consumer and provider interact using the Simple Object Access Protocol (SOAP) that provides a standard messaging format

It consist of a root element called envelope that contains a header and a body

  • typically trasmitted over HTTP

  • With GET the response is a SOAP message, the request optionally
  • With POST both request and response are SOAP messages

Via WSDL, clients can automatically understand:

  1. What a service can do
  1. Where the service is located
  1. How it can be invoked

A WDSL message is an XML document and it comprises of two sections:

  1. The Service Interface Definition, which defines, in an abstract manner the service. It comprises:
    1. the type of data (types)
    1. the messages exchanged between requestor and provider (messages)
    1. the operations that can be performed (portType)

  1. The Service Implementation Definition, which defines in a specific manner how the service is invoked. It comprises:
    1. how to transfer the messages (binding) and
    1. how to invoke the service (service)

  • binding provide the communication protocol, data format, and message encoding style.

Rest

SOAP is too complex and introduces overheads → The Representational State Transfer (REST) has been introduced as valid lightweight alternative for WS

  • client server architecture, using HTTP as transfer protocol
  • data still trasmitted using XML, but the overhead of SOAP is removed
    • Also JSON and plain text is available in Rest (just change the Content-Type header)
  • Parameters can be included in the request (embeddded in the URI), or as payload to be sent to the service

JSON is based on a subset of JS, text format and language independent

  • Lightweight data encoding, based only on two structures:
    1. Collection of name, value pairs
    1. Ordered list of values (array)

Crud

There are no strict rules of mapping functionalities to methods and URI

  • unwritten rules in order to make it more uderstandable
  • No mechanism to force the mapping

CRUD → major functionalities (create, read, update, delete), typically associated with databases

  • can be mapped in the four method of HTTP
  • PUT update and POST to create
