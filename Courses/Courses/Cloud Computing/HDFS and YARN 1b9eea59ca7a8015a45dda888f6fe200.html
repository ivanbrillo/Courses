HDFS and YARN

Hadoop Distributed File System

Manages storage across a network of machines in a cluster (creation, modification and deletion)

  • Designed to run on clusters of commodity hardware
  • Does not require expensive, highly-reliable hardware
    • Highly fault-tolerant
    • Failures are the norm rather than the exception

Files are divided into chunks (or blocks)

  • Typically 64/128 megabytes in size (even bigger)
  • Blocks are replicated at different compute nodes (usually 3+)
  • Nodes holding copies of one block are located on different racks
  • Block size and the degree of replication can be decided by the user
  • A special node (the master node) stores, for each file, the positions of its blocks → master-slave architecture
    • The master node is itself replicated

Large chunks to minimize the cost of seeks

  • The block abstractions allows a file to be larger than any single disk

HDFS cluster consists of a single Namenode, a master server that manages the file system namespace and regulates access to files by clients.

  1. Maintains filesystem tree
  1. Files metadata
  1. File-to-block mapping
  1. Location of blocks (i.e., on which datanodes)
  1. Access permissions

There are a number of Datanodes, usually one per node in a cluster.
Datanodes store and manage the actual data blocks.

  • A file is splitted into one or more blocks, and blocks are stored in Datanodes.
  • The Datanodes manage storage attached to the nodes that they run on.
  • Datanodes serve read/write requests, perform block creation, deletion, and replication upon instruction from Namenode.
  • Each Datanode sends a heartbeat message periodically to the Namenode.

This client is an interface between the actual clients (mapper and reducers) and the HDFS → they doesn’t communicate directly for the principle of abstraction

  1. The block locations will be returned in a list ordered by the proximity of the client to the data (choose the right replica to reduce data transfer)
  1. The actual client, call only three methods: open, read, close → high level

The network is represented as a tree and the distance between two nodes is the sum of their distances to their closest common ancestor

Distance between dist(n1,n2)=2dist(n_1, n_2) = 2dist(n1​,n2​)=2﻿ and dist(n1,n3)=4dist(n_1, n_3) = 4dist(n1​,n3​)=4﻿

  • Minimize the distance in this way

The namenode performs various checks to make sure the file doesn’t already exist and that the client has the right permissions to create the file.

  • Output stream is responsible for asking the namenode to allocate new blocks by picking a list of suitable datanodes to store the replicas

How does the name-node choose which datanodes to store the replicas on?

  • First replica on the same node as the client
    • For clients running outside the cluster, a node is chosen at random
  • Second replica on a different rack from the first, chosen at random
  • Third replica on the same rack as the second, but on a different node chosen at random
    • Further replicas are placed on random nodes in the cluster

YARN

YARN provides its core services via two types of long-running daemons:

  1. a Resource Manager (one per cluster) to manage the use of resources across the cluster
  1. a Node Managers (one per node in the cluster) to launch containers and monitor usage of container resources, reporting stats to resource manager

A container is a set of computer resources allocated to run an application specific process (e.g., a map or reduce task).

  • are not tagged for map or reduce tasks
  • not predefined amount of resources. Tasks can request what they need
  • The task can express locality constraints on which it want to be executed
    • If the locality constraint cannot be met, no allocation is made or the constraint can be loosened (e.g., on another node in the same rack) or delay scheduling

For each job the resource manager run an application master process inside a node manager container. It will:

  1. Request more containers from the resource managers and use them to run a distributed computation
  1. Takes the duty to monitor Tasks

YARN Scheduling

Provide different schedulers that allocate resources to applications based on different policies

FIFO scheduler

The FIFO Scheduler places applications in a single queue and runs them in the order of submission (first in, first out)

  • job2 is starving until job1 terminates

Capacity Scheduler

The Capacity Scheduler has separate queues

  • Each queue dedicated to an user of the cluster

Each queue configured to use a given fraction of the cluster capacity (not equal)

  • This is the default scheduler

  • Within a queue, applications are scheduled using FIFO scheduling
  • A large job finishes later than when using FIFO Scheduler

The problem is the waste of resources

Fair Scheduler

There is no need to reserve a set amount of capacity (no queue)

  • It will dynamically balance resources among all running jobs
    • E.g., when the first job starts, it gets all cluster resources. When the second job starts, it gets half of the cluster resources, and so on
  • Fair scheduling is per-user (not per job): if user A submits two jobs and user B only one, then each A’s job gets 25% while B’s job gets 50% of resources

Delay Scheduling

Variant of Fair or Capacity scheduler, that can be activated

  • All YARN schedulers try to honor locality requests → move process to the data

On a busy cluster, however, there is a good chance that a required node is saturated by other containers at the time of a request

  1. We can loosen the constraint by allocating resources on another node on the same rack (consume network only between two nodes)
  1. We can wait a short time to increase statistically the chances of being allocated in a container on the same node → more efficient (delay scheduling)
    • After some seconds, if it cannot be allocated, it will be executed on another machine

Every node manager in a YARN cluster periodically sends a heartbeat request to the resource manager

  • Heartbeats carry information about the node manager’s running containers and the resources available for new containers
  • Each heartbeat is a potential scheduling opportunity for an application to run a container
  • When using delay scheduling, the scheduler doesn’t simply use the first scheduling opportunity it receives, but waits for up to a given maximum number of scheduling opportunities to occur before loosening the locality constraint

Fault Tolerance

In order of increasing criticality

The application master will try to avoid rescheduling the task on a node manager where it has
previously failed

  1. Task Failure (map or reduce) → least serious case
    1. The user code in the task throws a runtime exception
      • The task JVM reports the error back to its parent application master before it exits.
      • The application master marks the task attempt as failed and frees the container resources
    1. Sudden exit of the task JVM
      • The node manager (that senses the fail) informs the application master
      • The application master marks the task attempt as failed and frees the container resources
    1. Hanging tasks
      • The application master notices that it hasn’t received a progress update for a while
      • The task JVM process will be killed automatically after this period (typically 10 minutes) → try to execute on another node
      • The application master marks the task as failed

2. Application Master Failure

  • Application master periodically sends heartbeats to the resource manager.
  • The resource manager will detect the failure and start a new instance of the master running in a new container (managed by a node manager)
  • The client needs to go back to the resource manager to ask for the new application master’s address (this process is transparent to the user)
  • If a MapReduce application master fails twice it will not be tried again and the job will fail

  1. Node Manager Failure → more critical because more applications could be controlled by the node manager
    • Node managers periodically send heartbeats to the resource manager
    • The resource manager will notice a node manager that has stopped sending heartbeats
      if it hasn’t received one for 10 minutes
    • The resource manager will remove it from its pool of nodes to schedule containers on
    • Any task or application master running on the failed node manager will be considered
      failed and will be therefore recovered by using the mechanisms seen before
    • Node managers may be blacklisted if the number of failures for the application is high
      (even if node manager itself has not failed)
      • Blacklisting is done by the application master

4. Resource Manager Failure

  • Failure of the resource manager is serious: without it neither jobs nor task containers can be launched
  • In the default configuration, the resource manager is a single point of failure
  • To achieve high availability, it is necessary to run a pair of resource managers in an active-standby configuration
  • Information about all the running applications is stored in a highly available state store
  • The standby resource manager can recover the core state of the failed active resource manager
  • he transition of a resource manager from standby to active is handled by a failover controller
    • The default failover controller uses leader election mechanism to ensure that there is only a single active resource manager at one time
    • Clients and node managers must be configured to handle resource manager failover. They try connecting to each resource manager in a round-robin fashion until they find the active one
    • It doesn’t introduce a new point of failure because it works in a similar way of blockchain. Distributed component that achive decisions (election of the new resource manager) based on the majority of them
    • Read the checkpoint file and start from there

Speculative Execution

Problem: Stragglers (i.e., slow tasks) significantly lengthen the completion time of
the job. Tasks can be slow due:

  1. Hardware degradation
  1. Software misconfiguiration

Solution: Speculative execution: application master tracks the progress of all tasks of the same type (Map and Reduce) in a job (need to complete all the maps to start the reduce). When the tasks are struggling (above some time) then:

  • Launches speculative duplicate tasks for the small portion of tasks that are running significantly slower than the average
  • Whichever one (i.e., original and speculative) finishes first, “wins”. The other is killed.
  • Additional cost: a few percent more resource usage

Each time the memory buffer reaches the spill threshold (80% by default), a new spill file is created by the spiller (thread in JVM), so after the map task has written its last output record, there could be several spill files.

  1. every spill file, before being written on disk is sorted and then passed by the combiner (if defined)

  1. reduce task will copy the partition on the local disk of the mapper to theirs, as soon as a map task has finished
  1. then merge the different files and sort them
  1. call the reduce function for each key - list of values
