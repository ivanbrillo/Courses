Application Architectures

For now, the cloud is an infrastructure offering the possibility to create VMs

  • VMs have also a virtual network adapter, through which they can communicate with other VMs via a (virtual or physical) LAN or with external hosts
  • VMs can have access to a cloud storage, a physical or virtualized storage shared among all the VMs usually accessed via the LAN that connect the VMs

Traditional Application (legacy)

  1. At the core we have an application server (single server), which runs the service implementing the logic of the application
    • The application server is a physical server, on which the service runs, data is stored in its local hard disks
      1. On one other end, we have a simple lightweight client, e.g. a web browser or a desktop/mobile application that provides the users the interface to the system, a web page or the application’s Graphical User Interface (GUI)

Clients and the application server communicate typically using the local network, or some wide area network

Cloudification

Cloudifications is the first step in bringing applications and services to the cloud

  • It means to move, as they are, their implementation on the cloud, transferring data and services from physical hardware installed on premises to VMs in the cloud
  • The overall architecture of the system remains intact: services are installed into VMs, users interact with clients installed into smartphones or PCs
  • The interaction between clients and the application server is still performed over a network (the Internet)

  1. Cheaper (hardware, personell, energy, location)
  1. More efficient applications

This is not cloud computing:

  1. Not scalable → in cloud computing, the resources may seem infinite to the application
    • The code not changed and uploaded to the cloud will exploit only vertical scalability, bounded by the resources of the physical server

Cloud Applications

Cloudification does not create true native cloud applications, it simply moves existing implementations to the cloud in order to benefit from some of the benefits provided by cloud computing, mainly cost reduction

  • Cloud computing, as we saw, does not only provide cheap computing, storage and networking capabilities, it offers other advantages, like scalability, higher reliability, the capacity to handle big data
  • Keeping the traditional architecture for cloud applications does not help in exploiting the full capabilities or advantages of cloud computing
  • In order to ensure that, cloud applications should be redesigned, following a different model depending on the requirements of the application and the use-cases

Cloud applications are usually implemented as multi-tier systems: the different functionalities are split among different VMs, each one running a specific functionality

  • The simplest basic architecture is a two-tier architecture that separates the functionalities to manage the data from the application server
  • Applications interact with the database tier to retrieve the data required to handle client requests or to store the data coming from the clients

If required multiple tiers can be adopted

  • For instance, storage functionalities could be extrapolated from the database tier, introducing an additional tier that manages only data storage
  • Tiers are organized in a chain of interactions, with inputs that is the output of the previous. Then inverse path

The tiers are connected through a LAN and use an application protocol, which can be implemented by a middleware software to simplify the development

Functionality of one tier, are implemented by more then one VM running the same code. Useful for:

  1. Load balancing
  1. Preventing a single point of failure

The set of VMs belonging to same tier implementing the application is named compute cluster

  • A compute cluster, in general, is a set of VMs organized to perform a collective computation over a single large job or a set of single requests
  • They also use a middleware to handle communication

High Availability (HA) Clusters

HA clusters are designed to be fault tolerant and support the execution of services that requires to be always available

  • HA clusters operate with redundant nodes to sustain faults or failures and avoid single point of failures
    • In each tier multiple VMs that perform the same operations

Redundancy is managed in a tier by selecting a VM in the tier as master and setting the others as slaves

  • Slaves are configured to behave as backup, i.e. backup instances that kick in every time the master fails
  • An election procedure, or a static order, is adopted to select the slave that is going to behave as master during a failure
  • In order to be able to offer the same functionalities of the master, some replication mechanism must be included to replicate data, configuration or settings also on the slaves as they change in the master

Load-Balancing (LB) Clusters

LB clusters are designed for higher resource utilization through load balancing among all the participating nodes

  • The goal is to ensure scalability: as a result, all nodes share the workload
    • higher resource utilization and higher performance, such as a lower response time

Load balancing is achieved by introducing an additional tier between the application tier and clients, the load balancer tier

  • it takes the clients requests and forward them to one of the VMs eg following the rule of less loaded instance

Data syncronization:

  1. Data replication
  1. Shared storage tier can be introduce to make the same data accessible from all the instances (data sharing complexity is on the storage tier)
    • avoid the overhead of data replication

Compute Intensive (CI) Clusters

Clusters designed to handle a large amount of data (eg. big data analysis)

  • Adopts a divide et impera approach

  1. Divide the tasks in multiple sub-tasks (jobs) and the data in multiple chunks, each of them assigned to a job
  1. Assign job, chunk tuple to a single server (worker) for analysis
  1. Different workers return the results to a collector, that merges the results

An example of a simple application is a web search algorithm, the world-wide web data is too much for a single machine to handle, the set of data to analyze (search for a specific keyword) is divided into chunks and assigned to different workers, a collector receives and aggregates the results received from the workers

  • In order to guarantee at the same time scalability to a large number of request an initial load balancer tier is usually adopted (mandatory if the application is a public application, e.g. a web search engine)
  • An instance in the application tier divides the data into chunks and creates the list of jobs
  • The initial dataset is stored in a shared cloud storage, as it is impossible to contain all the data in the local storage of different VMs and synchronize the content, due to its size
  • Jobs are dispatched to a set of workers, which belongs to a distributed processing infrastructure

To limit communication overhead, the batch processing infrastructure tier can have access to the storage tier

Conclusions on clusters

  • LB and CI architectures, with a load balancing tier, are ready to scale horizontally, as traffic increases new VMs are created and included in the tier, so the load on each one can be reduce
    • Contrarily, as load decreases VMs can be deallocated, so resources are not wasted
  • In the HA architecture, instead, horizontal scalability can be exploited to improve redundancy (more VMs means more availability) or to rebalance the tier in case of failure
