Msg Oriented DS and Data Replication

VMs host different functionalities. Such VMs are clustered into tiers, in which the VMs are replicated in order to ensure high availability and scalability

  • Requests from clients are received by VMs of the first tier (frontend tier) and then dispatched to others tiers (backend tiers)
  • The frontend is typically implemented as RESTful interface

A service oriented architecture is adopted: each VM hosts one (or more) self-contained software component, referred as service, that interact with others via message passing, that can be done via:

  1. SOAP → decreased utilization, typically used in the front/back communication (two developers teams that collaborate)
    • less interoperability
  1. REST → usually implemented as interface with clients for its semplicity (rapid developement for external companies)

Both SOAP and REST adopt a Request-Reply communication protocol

  • synchronous communication (client block until the reply arrives from the server)
    • Also called time-coupled since for some period client and server share the timeline → syncronized
    • Reliable because the reply act like an ack (also since in TCP everything is ack)
    • Direct communication betwen the two (client knows the adress of the server)
      • also called space-coupling → because they need to be in direct communication

The most implemented in client-frontend interface because it is the simplest and time and space coupling is ok (In an app I want a response before go forward)

The backend is expected to have a varying number of VMs to support scalability (load balancing) or availability (data replication)

  • Supporting such dynamicity is important: the space and time coupling is not suited to ensure scalability in the communication inside the backend

An indirect communication paradigm is required to ensure:

  1. Space uncoupling: the sender does not know or need to know the identity of the receiver(s), and vice versa.
    • Senders/Receivers can be replaced, migrated, replicated at runtime
  1. Time uncoupling: sender and receiver(s) have independent lifetimes.
    • In a volatile environment the sender and receiver(s) do not need to exist at the same time to communicate (VMs can be destroyed/created dynamically)
    • Per esempio nel transitorio dove altre VM sono create, tutte le richieste dal frontend devono essere gestite da VMs già create, non da quelle future

Introduce an intermediary between tiers in order to achive space and time uncoupling

  • decrease overhead, more throughput

Indirect Message Oriented Communication

Source and destination does not open a direct communication channel (TCP-UDP channel), but rather the sender injects the message into a bus

  • the communication bus is implemented by an intermediary: the sender forwards the message to an intermediary, which takes care of forwarding the message to the receiver, and vice versa
  • Different types of intermediary has been defined:
    1. broker
    1. message queue

Broker

A Publish-Suscribe system is a system where senders (named producers or publishers) publish structured data, while receivers (named consumers or subscribers) express interest on a specific type of data through subscriptions

  • At the core of the system, we have the message broker, which is responsible for relaying the data from publishers to subscribers
  • The result is a one-to-many communication

Could define different filtering for subscriptions

  1. channel based communication: create channels intially identified by a name
  1. Topic-Based: defined at runtime, based on names
  1. Type-Based: filtering based on types of events (different datastructures, no different names)

Message Queue

Provides a point-to-point message exchange between producer ad consumer

  • the sender places the message into a queue, and it is then removed by the receiver
  • Messages queues are implemented by the Message Queueing System

The operations offered by the queuing system is:

  1. send to put a msg in a queue
  1. blocking receive
  1. non blocking receive (polling)
  1. notify, issued by the message queuing system to notify a consumer that a new msg is available (need to subscribe to a queue before)
    • works like in the broker system, in alternative to avoid receive operations continously

Every message consists of:

  1. A destination (unique ID for the queue)
  1. metadata associated with the msg - like priority
  1. body of the msg → typically opaque for the message queue system

  • Typically FIFO queuing policy, but maybe also with priority
  • One crucial property of message queue systems is that messages are persistent: message queues will store the messages indefinitely (until they are consumed) and will also commit the messages to disk to enable reliable delivery
  • Message Transformation can be performed on arriving
    • change data format to deal with heterogenity of data representations (JSON to XML) or little endian to big endian

They are perfect for cloud applications, and comunications in deeper tiers

  • they can handle the varying number of VMs in a tier, since a new VM will poll a msg (nothing change for the upper layer)
  • same if a VM is destroyed

Message Brokers and Message Queuing Systems can be implemented in a centralized and distributed manner

  1. In a centralized implementation the broker is implemented in a single system
    • simple, however introduces a single point of failure, may be also a bottleneck
  1. In a distributed implementation a network of brokers/message queuing systems is adopted
    • more complex, however guarantees resiliency and scalability

The Advanced Message Queuing Protocol (AMQP) is one of the most widely adopted implementation for Message Queuing Systems

Data Replication

Data replication across the VMs of the same tier is required in order to ensure that they all work on the same set of data, so they can provide the same service to users

  • We need to ensure that the data across VMs are syncronized (the system must behave independently of the VM that handle my request) → the system must be consistent over time
  • scalability, availability and fault tolerance

Can be implemented in two ways:

  1. Generally, data replication is implemented via message exchange among the VMs of the same cluster
  1. When large datasets are involved, a shared storage is usually adopted across different VMs
    • exchange of data for coordination is still required

Requirements of data replication:

  1. Transparent: data replication must be transparent from users
    • they should access different copies of data without being aware of that
  1. Consistency: replicas should be consistent to each other
    • an operation performed on any replica should produce the same result
  1. Resiliency from VM failure, however it is assumed that network partitions cannot occur
    • reasonable since VMs are on the same LAN (same datacenter) - often redundant
    • Data replications mechanism often assume this, to assure availability and consistency (CAP theorem)

System Model

Each replica is stored in a different replica managers

  • Each replica manager accept read/query and update operations (typically in a recoverable manner → inconsistencies due to failure can be recovered)

Five phases to handle a single request form a client (general overview):

  1. A request is received by the frontend module that is issued to one or more replica managers (depend on implementation)
  1. Coordination: the replica managers that receive the request prepare to execute it. They can coordinate to execute immediatly or to delay the execution to mantain consistency
  1. Execution in one or more replica manager
    • The request is usually executed tentatively (in a manner that can be undone later if needed, e.g. to recover from faults)
  1. Agreement: the replica managers must reach consensus on the effect of the request. When agreement is reached, the execution of the request is committed, changes are applied (if any)
  1. Response: one or more replica manager respond to the frontend

Multiple phases exploit group communication among replica managers (the group members) for coordination and data exchange → multicast communication

  1. Reliable/Atomic: the msg is delivered to every alive member or to no member at all (equivalent to TCP)
    • duplicates are removed, loss of msgs are handled
    • no guarantee on the msgs order
  1. Total/Casual order: every member must receive all updates in the same order
    • if aaa﻿ HB bbb﻿ then every memeber must receive aaa﻿ before bbb﻿
    • No guarantees on absolute order (time of reception) across different members
  1. View-synchronous: with respect to each msg, all members have the same exact view all the time

Tradeoff between complexity and guarantees

1. Primary-Backup Replication

The simpler one. One replica managers is selected as the primary, responsible all the request coming from the front end layer

  • replicas to guarantee fault tolerance and high availability
    • waste of resources of the backups
  • the primary is also responsible for handling the sending of backup copies to the slaves
  1. Request: the frontend issues a request, the request contains a unique identifier, which identifies univocally the request
  1. Coordination: The primary handles requests atomically, in the order in which they have been received.
    • It checks the unique identifier, if the request has been already executed, the same response is sent back
    • No coordination with other replica managers is needed
  1. Execution: The primary executes the request and stores the response
  1. Agreement: If the request is an update, the primary sends the updated state, the response and the unique identifier to all the backups.
    • The backups send an acknowledgment. For this kind of communication atomic multicast is sufficient
  1. Response: the primary responds to the frontend, which hands back the response to the client

2. Active Replication

Different approach to guarantee high availability

  • replica managers are organized in groups → specialized to a particular functionality
  • frontends multicast their request to the group, so all the replica manager in the gropup can process the request independently and reply
    • identical reply since consistent data replication

If a crash occurs in any of the replica managers, there is no impact on the performance as the remaining replica managers can reply

  • the data sycronization is achived since all the request is done by the whole group

  1. Request: The frontend attaches a unique identifier to the request and multicast it to all the replica managers.
    • Total order multicast to ensure that requests are received in the same order by all the replica managers
  1. Coordination: No coordination is needed
  1. Execution: Every replica manager executes the request. Since the requests are delivered in total order, replica managers process the request identically
  1. Agreement: Thanks to the total order multicast, there is no need for agreement
  1. Response: Each replica manager sends its response to the frontend. Since is guaranteed that the responses are all equal → forward the first to arrive

Load Balancing Requirements

Passive/active approaches focus on providing high availability:

  1. In the passive approach, backup replicas do not take part at handling users request, consequently the load is all on the primary replica
  1. In the active approach the replicas serve the replicas in a redundant manner

A different approach has been defined to provide high availability and scalability at the same time:

  • Different replica managers are involved in handling requests from the frontend (not just one or all handling the same request), in parallel, thus maximizing utilization
  • Replica managers do not propagate updates in a prompt manner (as soon as they are available and before passing back control to the client), updates are deferred when possible, while the control is given back to the client as soon as possible (even before propagating the update to other replica managers)
  • Data maybe a little outdated

1. Gossip Architecture

In the gossip architecture, the replica managers exchange gossip messages periodically in order to convey the updates they have received from client

  • Clients are assigned to specific frontend instances for load balancing, even though they can change, if the assigned instance crashes

The service provides two basic types of operations:

  1. Query, which are read-only operations
  1. Update, which modifies the state of an object. The update operation does no read the state

The gossip system makes two guarantees:

  1. Each client obtain a consistent service over time
    • In answer to a query, a replica manager provides a response with data that reflects the last updates that the client has observed so far (its own updates)
    • A client receive an old (but consistent with his view of the system) information when a query is issued → Sequential consistency is guaranteed
  1. The consistency between replicas can be relaxed in time due to the frequency of the exchange of gossip messages

  1. Request: The front end normally sends requests to only a single replica manager
  1. Coordination: The replica manager that receives the request does not process it until it can apply the request according to the required ordering constraints.
    • This may involve receiving updates from other replica managers, in gossip messages.
    • If the client view is more updated than the one of the replica manager, it needs to wait and update, otherwise inconsistencies
  1. Execution: The replica manager executes the request
  1. Agreement: The replica managers update the data by exchanging gossip msgs
    • The updates are exchanged in a lazy fashion
  1. Response: If the request is a query, the replica manager replies after the execution, if it is an update, it replies right after receiving it

In order to keep ordering of requests, timestamps are adopted (to this aim FEs must have their clock synchronized)

  • Specifically, each FE keeps a vector of timestamps that reflect the version of the latest data values accessed by the client
  • This timestamp is sent to the replica manager (the field prev) together with the query
  • The replica manager supplies a new timestamp with the response (the field new)
    • This will replace the old timestamp in the FE
