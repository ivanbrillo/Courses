Introduction to RT Systems

In many cases, the real-time computer running the application is embedded into the system to be controlled (embedded systems)

Most RT applications rely on empirical techniques (trial and error):

  • Assembly Programming: used for the most critical sections of code to ensure maximum efficiency and control
  • Timing via Dedicated Hardware Timers instead of softwares
  • Control via Driver Programming
    ◦ Execution is triggered by hardware events through Interrupt Service Routines (ISRs)
    • The software doesn't decide when to run, the hardware forces it to run
  • Priority Manipulation (Heuristic)
    ◦ Priorities are manually adjusted or "tweaked" to force tasks to meet their deadlines

Disadvantages:

  1. Tedious programming which heavily depends on programmer’s ability
  1. Time consuming
  1. Difficult to understand Readability ≈ 1/efficiency
  1. Difficult software maintainability (understanding takes more that re-writing, that is error prone)
  1. Difficult to verify timing constraints without explicit support from the OS and the language

Consequences:

  1. The code produced by empirical techniques can be highly unpredicatable (we cannot test in all possible ways)
  1. Time constraints cannot be verified a priori → low reliability
    • Patriot system that uses ISR with disabled interrupt, and thus loosing some clock cycles in 100hours accumulated over 350ms of delay causing a miss

RT System defintion: A computing system where correctness depends not only on the logical output values but also on the time at which they are produced.

  • The system interacts with an environment, taking input X(t)X(t)X(t)﻿ and returning output Y(t+Δ)Y(t+\Delta)Y(t+Δ)﻿
  • REAL implies the system time is synchronized with the environment's flow
    • The system clock must be fast enough to detect and respond to changes. For example, a 2GHz system cannot serve a 5GHz environment
    • Real Time wrt the environment

Objection: It is not worth to invest in RT theory, because computer speed is increasing exponentially, and all timing constraints can eventually be handled.
Answer: Given an arbitrary computer speed, we must always guarantee that timing constraints can be met. Testing is NOT sufficient.

  • The objective of a real-time system is to guarantee the timing behavior of each individual task
    1. TDMA is suitable for RT system, meanwhile CSMA/CA no
  • The objective of a fast system is to minimize the average response time of a tasks set. This not guarantee that each task respects its temporal requirement

An RTOS is an OS responsible for:

  1. Managing Tasks
  1. Managing concurrency
  1. Activating periodic tasks at the beginning of each period (time management)
  1. Deciding the execution order of tasks (scheduling)
  1. Solving possible timing conflicts during the access of shared resources (mutual exclusion)
  1. Manage the timely execution of asynchronous events (interrupt handling)
  1. It implements mechanism to guarantee the predictable execution of task with real-time constraints

Handles differently the memory, scheduler, provides bounds and is more deterministic

Example of RTOS:

  • FreeRTOS
  • RT-Linux (RealTime Linux)
  • Linux with scheduling SCHED_DEADLINE instead SCHED_FIFO

A real-time task is characterized by a deadline, which is the maximum time within which it must complete its execution

  • In critical (real-time) applications, a result produced after the deadline is not only late but wrong.
  • A non real-time has no deadline

Classification (based on the implications of missing one):

  • Hard: A real-time task is said to be hard if producing the results after its deadline may cause catastrophic consequences on the system under control
    • someone dies if airbags are not inflated
    • guaranteed offline
  • Firm: A real-time task is said to be firm if producing the results after its deadline is useless for the system, but does not cause any damage.
    • Common in multimedia and networked systems, where freshness matters more than completeness → e.g. packets
    • guaranteed online
  • Soft: A real-time task is said to be soft if producing the results after its deadline has still some utility for the system, although causing a performance degradation
    • User interface commands processing

A real-time operating system that is able to handle hard real-time tasks is called a hard real-time system

  • should guarantee all thre types of tasks with different strategies

  1. Offline guarantees → check at compile time if the deadline can be met (statically)
    • all hard tasks should be guarded in this way (e.g. airbags, detection of critical conditions, …)
  1. Online guarantees → checks while running if the new task can met the deadline
    • Firm tasks should be guarded, aborting if the deadline cannot be met
      • Tasks that should meet deadlines, but if they can’t, it's better to skip the result rather than deliver it late.
    • Soft tasks should be handled to minimize their average response time
      • Tasks where delays are acceptable, since they mainly support user interaction or interface management

Predictability

A hard real-time system should be predictable

  • Based on the kernel features and on the information associated with each task, the system should be able to predict the evolution of the tasks and guarantee in advance that all critical timing constraints will be met
  • The reliability of the prediction could be affected by a lot of factor, thus we can add a margin of 10% to the worst case execution time (TexeT_{\text{exe}}Texe​﻿) WCET
    • To have the execution time I have to run different test with different possible input and pick the worst case of execution time of this task

What limits predictability:

  1. Architectural hardware features like cache/DMA, brench predictor, …
  1. Policies adopted in kernels (semaphores)
  1. Programming styles and languages (e.g. Java and GC)

DMA

DMA: A technique allowing peripheral devices to transfer data directly to/from main memory to relieve the CPU of I/O control tasks

  • Cycle Stealing: The DMA controller "steals" a memory cycle to execute a data transfer
  • If both the CPU and DMA require a memory cycle simultaneously, the Arbiter prioritizes the DMA. This is because incoming data is often RT and takes precedence to avoid data loss.
  • The CPU continues working if instructions/data are in the cache. However, if a cache miss occurs, the CPU must access main memory and is forced to wait for the DMA to finish.
    • Since it is impossible to predict how many times the CPU will have to wait for the DMA during a task, the response time cannot be precisely determined.

Solutions

In the memory time-slice method, each memory cycle is split into two adjacent time slots:

  • one reserved for the CPU
  • the other for the DMA device

This solution is more expensive than cycle stealing but more predictable (no conflicts)

Multi-Bus and Dual Port Memory

  • Dual Port Memory: Allows memory to be accessed through two distinct ports simultaneously, provided the accesses target different memory blocks (linker responsibility).
    • Double Buffering: A technique utilizing dual ports to overlap data transfer with computation (common in GPUs) [decouple consumer - producer]
      • While data is being transferred into Block 2 by the DMA, the CPU processes the data already in Block 1, then change
  • Multi-Bus Architecture: The CPU utilizes dedicated buses for different tasks (DMA, I-BUS for instructions, D-BUS for data).
    • Parallelism: The CPU can fetch an instruction from the I-BUS while simultaneously accessing data on the D-BUS.

Cons: Significant increase in power consumption

Bus Matrix in ARM Architecture: A complex interconnect system (crossbar switch) that allows multiple Masters (components that initiate transfers) to communicate with multiple Slaves (components that respond) simultaneously.

  • Bus Types:
    • AHB (Advanced High-performance Bus): Used for high-speed components like the CPU, DMA, and main memory (SRAM/Flash)
    • APB (Advanced Peripheral Bus): Used for slower peripherals (Timers, UART, GPIO)
  • Memory Banking: SRAM is often divided into distinct "banks" (e.g., 16KB or 32KB blocks).
    • This physically separates addresses, allowing the DMA to write to one bank while the CPU reads from another without stalling.

  • If I have a variable A and, at the same time, the CPU wants to compute something else, the code and the variable A must reside in different memory banks. The linker performs this allocation automatically
    • Otherwise, we have to use double buffering, but is more costly

Cache

A cache is a small fast memory that holds copies of some of the contents of main memory

  • needed for high performance systems
  • The cache speeds up average memory access time when properly used (working set)
  • Performance may degrades depending on the input data → problems with predictability

Solutions to unpredictability

  1. Cache is disabled
  1. Execution time increased by a constant factor
    • just an approximation, I don’t know if I computed the worst case
    • just for soft or firm RT tasks
  1. Consider every access as miss and compute the worst time
  1. Use tools that estimate the number of miss/hit and produces a right estimate of WCET (worst-case execution time)

Interrupts

The interrupt mechanism is utilized to manage efficiently I/O operations

  • Interrupts allow devices to signal the cpu and to force the execution of particular pieces of code (Interrupt handler routine, driver)
    • To get data from an I/O device, each task must enable the hardware to generate interrupts, wait for the interrupt, and read the data from a memory buffer shared with the driver
  • Is an alternative to busy waiting or DMA
  • Request (intr request): The Device sends this to the CPU to indicate an event has occurred.

  • Acknowledgement (intr ack): The CPU completes its current instruction (in the IR), saves its current location (from the PC), and sends this signal back to confirm it is ready
  • Data Transfer: The CPU interacts with the device via the data/address bus to service the request.
  • Key Registers:
    • Status Register: The CPU reads this to understand why the interrupt happened
    • Data Register: Holds the actual data being transferred to or from the CPU

Since I don’t know how many times an interrupt may happen to a task I have a non-determinist component on the delay of a task (not the execution time, that is constant)

In many operating systems, interrupts are served using a fixed priority scheme

  • Each driver is scheduled based on a static priority, higher than process priorities
  • This rule is motivated by the fact that interrupt handling routines usually deal with I/O devices that have real-time constraints, whereas most application programs do not

Solutions

Polling in user level

All external interrupts are disabled, except the one from the timer (necessary for basic system operations) → we do not allow devices to trigger interrupts

  • all peripheral devices must be handled by the application tasks, thus the polling’s cost is related to this task
  • they have direct access to the registers of the interfacing boards
  • data transfer takes place through polling

Advantages:

  1. The time needed for transferring data can be precisely evaluated and charged to the task that performs the operation (e.g. looking at the ADC datasheet)
  1. The kernel does not need to be modified as the I/O devices are replaced or added

Disadvantage:

  1. Busy Wait
  1. Application tasks must know all low-level details of the devices that they want to handle
    • However, this can be easily solved by encapsulating all device dependent routines in a set of library functions that can be called by the application tasks.

Polling in the kernel

  • All external interrupts are disabled, except the one from the timer
  • The devices are managed by dedicated kernel routines, periodically activated by the timer → all the I/O operations are done via these tasks
  • Their computational load can be computed once and for all and taken into account through a specific utilization factor

Advantages:

  1. The unbounded delays due to the execution of interrupt drivers are eliminated
  1. Hardware details of the peripheral devices can be encapsulated into kernel procedures and do not need to be known to the application tasks
  1. The data can be accessed by more than one task

Disadvantages:

  1. Busy wait
  1. Higher system overhead than A, due to the context switches between user and kernel modes
  1. The device handling routines are part of the kernel that needs to be modified if new peripheral are added or replaced

ISR with a server task

  • All external interrupts enabled (so I/O can trigger them at any time)
  • Drivers (ISR) have the smaller possible size → the only purpose of each driver is to activate a proper task that will do the work
  • The device manager task (the one triggered by the ISR) is guaranteed and scheduled like any other application task.
  • It may have temporal constraint depending on application requirements
  • A control task can have a higher priority than a device handling task

Advantages:

  1. busy wait during I/O operations are eliminated
  1. the task execution times become more predictable, since everything is handled by normal tasks and not by driver

Disadvantages:

  1. A little unbounded overhead due to the execution of the small drivers
    • It should be taken into account in the guarantee mechanism.
    • However, it can be neglected in most practical cases.

If I have data that are particularly important, then I could do directly pooling, instead of using the interrupt

System Calls

In order to precisely evaluate the worst-case execution time of each task, all kernel calls should be characterized by a bounded execution time.

  • It is desirable that each kernel primitive should be preemptable (as much as possible) → interrupt enabled.
    • In fact, any non-preemptable section could delay the activation or the execution of critical activities, causing a deadlines miss

Semaphores

Mutual exclusion semaphore as implemented in traditional system can cause the priority inversion problem

  • it introduces nondeterministic delays on the execution of critical tasks with higher priorities
  • Solutions: use specific alogirthms to avoid and bound waiting (e.g. priority inheritance)

Memory Management

Also memory management techniques (virtual memory) must not introduce non-deterministic delays during the execution of real-time activities.

  • demand paging schemes are not suitable to real-time applications subject to rigid time constraints because of the large and unpredictable delays caused by page faults and page replacements.
  • Typical solutions adopted in most real-time systems adhere to a memory segmentation or a static partitioning (FreeRTOS) rule with a fixed memory management scheme.
    • Disadvantage: fragmentation
    • We cannot use malloc() , because it uses a complex algorithm to find free memory, that is not deterministic → instead we use primitives exposed by the RTOS

Programming Languages

In programming languages specific for real-time systems, specific statement have been added and different constructs have been eliminated to limit unpredictability:

  • recursion limits the time analysis
  • dynamic structure have problems with the allocation of memory
  • only time bounded loops

  1. Languages for Static RT System → all tasks are scheduled at compilation time
    • Real-Time Euclid allows the classification of processes as periodic or aperiodic and provides statements for specifying activation time, period and deadlines
  1. Languages for Dynamic RT System → allows dynamic creation and destruction of tasks
    • provides facilities to specify periodicity and deadline constraints, to seek guarantees that timing constraints will be met, and to perform alternative actions when either the timing constraints cannot be met
