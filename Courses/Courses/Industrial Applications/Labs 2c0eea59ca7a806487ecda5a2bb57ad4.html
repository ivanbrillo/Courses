ARM and STM32

ARM develops the architecture and licenses it to other companies

Cortex (processors family) Profiles

Cortex-A, which stands for Application

  • complex tasks like hosting a rich OS (androids)
  • Based on out of order (OOO) architecture
  • cache, TLS, and support VM

Cortex-R, which stand for Real-Time

  • embedded systems where reliability, high availability, fault tolerance, maintainability and deterministic real-time response are essential
  • They include lock-step executions, ECC protection on memory (Error Correction Code with parity bits)
  • lock-step execution: 2 cores executing in the same time the same things, and check if errors occurs, then throw an exception
    • With 3 I could adopt a majority voting and correct also

Cortex-M, which stands for eMbedded

  • Designed for the low-cost embedded market
  • High energy efficiency

STM32 Microcontrollers

STM32 is a broad range of microcontrollers divided in nine sub families

  • STM32 buys the Cortex M design from ARM, puts it into a piece of silicon, adds memory (Flash/RAM) and peripherals (timers, USB, pins)

Cortex M3-M4 Architecture

3 stage pipeline: Fetch, Decode, Execute

  • HW divide and HW single cycle multiply
  • Simplified Branch Predictor → detect an if and fetch the next instruction

Nested vector interrupt unit (NVIC): Each interrupt can be assigned a priority level, which defines the processing order in case of concurrent interrupts

  • the lower the higher priority (inverse or RT system)
  • The NVIC provides fast and deterministic interrupt handling
    • Perform the context switch in just 12 CPU cycles
  • The NVIC also contains a standard timer with auto-reload to provide periodic interrupts

Wakeup interrupt controller (WIC)

  • It is a small area of the Cortex-M processor that is kept alive when the processor is in low-power mode
  • The WIC can use the interrupt signals from the microcontroller peripherals to wake up the Cortex-M processor
  • Useful feature for embedded devices

MPU (Memory Protection Unit)

  • Define privileged and unprivileged regions over the 4 GB address space
  • If the CPU is running in unprivileged mode and it tries to access a privileged region of memory, the MPU will raise an exception and triggers the fault service routine

It introduces a hardware floating-point unit (FPU) for 32bit precision arithmetic

  • Support efficient digital signal process (DSP) hardware instructions
    • It uses SIMD (Single Instruction, Multiple Data): Hardware that processes multiple small data points (like audio samples or pixel colors) in a single clock cycle

  • The hardware multiply accumulate (MAC) has also been improved so that many of the 32x32 arithmetic instructions are single cycle (or few cycles)

Harward bus architecture

  • They have a port for fetching instructions from code memory and a port for accessing SRAM. A third port is used to access peripherals
  • Implemented as a bus matrix

STM Developement Kits

  • Nucleo boards → have arduino connectors, fast prototyping
  • Discovery kits → often include extra hardware (as display, accellerometer, …), cheap
  • Evaluation boards (EVAL) → complete with all the external circuits (tranceiver, …), expensive

STM32Cube Software Library

The STM32Cube firmware is designed as a layered architecture

It consists of three main levels:

  1. Level 0: this is the lowest software layer that interacts directly with the hardware. It includes three distinct types of drivers:
    • HAL (Hardware Abstraction Layer) HAL_GPIO_WritePin(GPIOA, GPIO_PIN_5, GPIO_PIN_SET)
      • Provides a high-level, generic, and portable (across micros) set of APIs to interact with peripherals (timers, UART, SPI)
      • HAL uses LL
    • LL (Low Layer) Drivers:
      • Offers a faster, light-weight, and register-level access to the hardware
    • BSP (Board Support Package) BSP_LCD_Init() HAL_Delay(100) BSP_LED_On(LED3)
      • Drivers specifically for the external components mounted on the development board (not inside the chip), e.g. touch screen, …
      • BSP uses HAL
      • Split in two categories:
        • generic APIs which provide common and generic functions to all the STM32 Series
        • extension APIs provide customized functions for a specific family
  1. Level 1: Middleware Components

    This layer sits on top of the drivers and provides complex software libraries and protocols → hardware independent

    • RTOS → uses HAL drivers
    • Graphics: Graphical libraries for driving displays and creating GUIs.
    • Others: e.g. TCP/IP networking
  1. Level 2: Application Layer

    It includes a demonstration based on the middleware service layer, the low-level abstraction layer and the applications that make basic use of the peripherals for board-based functions

Software Timers

Software timers are implemented and controlled by FreeRTOS kernel

  • They do not require hardware support, and are not related to hardware timers
  • They use only hte systick timer and have the same resolution (1ms)
    • If more resolution is needed, must opt for HW timers

FreeRTOS uses a centralized thread, named RTOS daemon, which automatically calls the callback routines when a timer expires

  • Callbacks must be short otherwise delay others
  • osTimerDef(timerID, timerCallback) and I can create, start and stop timers

Signals

Signals, which act as a lightweight mechanism for tasks to communicate and synchronize

  • A signal is simply a flag (lighweight), not a heavy data structure like a queue or semaphore
  • Based on two procedures:
    • osSignalSet(osThreadId thread_id, int32_t signals)
    • osSignalWait(int32_t signals, uint32_t millisec)
      • Pauses the current thread (blocking state) until specific flags are received (maximum wait of millisec)
      • osEvent is the struct returned, useful to understand what happened

First solution for executing threads with a fixed period

  • NOTE: It is wrong to implement complex logic inside a Timer Callback or ISR.
    • They must be extremely short (non-blocking) to avoid freezing the System
    • Implemented inside a timer, the task wouldn’t be preemptive nor with correct priorities

FreeRTOS

Cortex Microcontroller Software Interface Standard (CMSIS) is a vendor independent hardware abstraction layer for microcontrollers that are based on Arm Cortex processors

  • FreeRTOS can be used with or without CMSIS interface → CMSIS-RTOS API
  • Useful if i want to change OS or Micro without rewriting the whole codebase

FreeRTOS only provides the core real-time scheduling functionality, inter-task communication, timing and synchronization primitives.

  1. OpenRTOS → same code as FreeRTOS but commerial (warrenty and legal protection)
  1. SafeRTOS → developed in compliance with safety standars

Threads share the same address space → threads are named tasks in freeRTOS

A TCB (Task or Thread Control Block) is allocated for each thread

  • It is a descriptor of the thread, and contains all relevant information related to the thread execution (priority, the stack pointer, the program counter, CPU registers etc
  • Semaphores may have the unbounded priority inversion, while mutex implements priority inheritance protocol

There is a config file for scheduling algoithms, priority of system threads, number of priorities (thus numeber of queue)

  • The scheduler is a priority based scheduler
  • Threads priorities (max 3) are different from interrupt priorities
    • Interrupts always preempt a thread
    • Interrupt priority (decreasing) is important when more interrupt are raised

In thread I cannot put a return, but I must have a osThreadTerminate(NULL) → remove TCB and memory

They are all fixed priority and preemptive:

  • Preemptive + Time Slicing: High priority tasks interrupt low priority ones immediately. If two tasks have the same priority, they share the CPU by taking turns (round-robin) every tick.
  • Preemptive without Time Slicing: High priority still interrupts. But if two tasks have the same priority, the one currently running keeps the CPU until it chooses to yield or blocks. It does not share automatically.
    • Turning time slicing off results in a reduction in the scheduler’s processing overhead
  • Cooperative: No interrupts. A task runs until it explicitly gives up the CPU (osYield or osDelay).
    • system less responsive
